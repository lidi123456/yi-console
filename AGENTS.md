# AGENTS.md

See [README.md](README.md) for an overview and usage. This file records the conventions you need to know when changing code.

## Map

- `crates/proto`: the single source of truth for the protocol. To add a method, first add a constant in `methods`, then extend the dispatch in `crates/yi-agentd/src/server.rs`; the frontend types in `app/src/types.ts` are kept in sync by hand.
- `crates/yi-agentd/src/hub.rs`: the session state machine. Every event goes through `emit()` to be numbered, persisted and broadcast; adapters must not write to the database directly.
- `crates/yi-agentd/src/adapters/`: one file per tool, all implementing `AdapterCmd` input and `Emitter` output. The ACP tools (Cursor / Kiro / Qoder / CodeBuddy) share `acp.rs`. For what a new tool needs and how to keep it consistent with the existing ones, see [docs/adding-a-tool.en.md](docs/adding-a-tool.en.md).
- `crates/client/src/api.rs`: `ClientHub::call` is the complete set of commands the frontend can call. Tauri (`app/src-tauri/src/lib.rs`) and yi-web are thin wrappers around it.
- `app/src/store.ts`: frontend state and the event loop; components live in `app/src/components/`.

## Conventions

- Event fields are camelCase. `EventBody` uses `rename_all_fields = "camelCase"`, so new variants need no extra annotation.
- `assistant_delta` and `thinking_delta` are transient events with seq 0 and are not persisted. At the end of a turn, the complete `assistant_message` / `thinking` is authoritative.
- Queries that don't belong to a session, such as model lists and quotas, live in `crates/yi-agentd/src/probe.rs`: start the tool once, ask, exit; the working directory is `<base>/probe`.
- Tool detection is `crates/yi-agentd/src/tools.rs`: `fix_path` builds the daemon's PATH (inherited PATH, `YI_CONSOLE_PATH`, the login shell's PATH on Unix, the registry's system + user PATH on Windows, then common install directories that exist), and `detect` looks up fixed executable names on it. The daemon outlives the app, so `tools.detect` reruns `fix_path` before scanning; the "Re-detect" button in the new session dialog and saving host settings both call it via `redetectTools` in `store.ts`.
- Status line values computed on the host (git status, custom command) are in `crates/yi-agentd/src/statusline.rs`. The command input reuses the JSON fields of Claude Code's statusLine; our own fields only go under `yi_console`.
- Queued messages (`session.send` with `queue: true`) and permission mode switches live in `hub.rs`: when a turn ends, `Emitter::event` calls `after_turn()` to send the next message or restart the process. Adapters receiving `AdapterCmd::SetPermissionMode` should switch while running where possible; when they can't (Claude switching to allow-all), the hub restarts the process.
- git operations on session changes are in `crates/yi-agentd/src/gitops.rs`. Paths are always relative to the repo root; absolute paths and `..` are rejected. Every git command runs with `GIT_OPTIONAL_LOCKS=0` (the panel polls status, which would otherwise take `index.lock` and break an agent's commit), and `git.changes` returns at most 10000 files (`total` is set when more were left out).
- Usage stats (`stats.rs`): usage for Claude / Codex / Qoder / CodeBuddy is read from the tools' own logs (`~/.claude/projects`, `~/.codex/sessions`, `~/.qoder/projects`, `~/.codebuddy/projects`, cached by file mtime and size; Qoder's built-in models only record credits, CodeBuddy records both tokens and credits). For these four tools only cost (Claude) is taken from usage_log, to avoid double counting.
- "Version mismatch" = different version string or different `buildTime`. Builds from copied sources (no .git) are all `+dev`, and uncommitted changes keep the commit hash, so comparing only the version would miss upgrades; in both cases `build.rs` uses the current time as the build time.
- When the client connects and finds a version mismatch, it upgrades automatically (`ClientHub::auto_upgrade`). The local host always upgrades; SSH hosts only upgrade when the client's `build_time()` is newer than the daemon's, so two computers on different versions don't keep overwriting each other; relay hosts only get a notice. If turns are running, it waits for them to end (`upgrade` event with phase=waiting, only a corner notice in the UI); during upload and restart the frontend shows a full-screen overlay (`Upgrade.tsx`). Each host is auto-upgraded at most once per app run.
- `DAEMON_VERSION` includes the commit hash (`crates/proto/build.rs`; CI uses `GITHUB_SHA`), which the client uses to prompt restarting an old daemon. Don't change it back to just the package version.
- tmux for terminal mode is wrapped in `crates/yi-agentd/src/tmux.rs` (when `StartSpec.tmux` is set, the pty adapter uses `tmux -L yi-console new-session -A`); on daemon start, `Hub::reattach_terminals` reattaches sessions that are still alive. Only an explicit stop / delete by the user runs `kill-session`; when the adapter's command channel closes (process swap), only the tmux client ends.
- xterm keeps no scrollback in terminal mode (tmux redraws the whole screen each time); scrolling up goes through `pty.scroll`, which puts tmux into copy-mode, and the frontend draws its own scrollbar; typing exits copy-mode first. The tmux status query on mount often comes before the tmux session exists, so until tmux is confirmed, ask again every 3 s (at most 20 times), otherwise the scrollbar never appears. Terminal padding goes on `.xterm` (`--term-pad`), not on the `.term` container: under global border-box, FitAddon counts container padding in the height and the extra line ends up under the status bar.
- Terminal sessions (`mode: terminal` or shell) wait in `hub.rs`'s `start_when_sized` for the first `pty.resize` before starting the process (up to 3 s), and the frontend debounces resize by 200 ms: full-screen programs like cursor-agent and Claude Code leave ghost artifacts when resized right after starting.
- The chat area imitates Claude Code's timeline (`ToolLine` in `ChatView.tsx`): `toolName()` normalizes tool names to Bash / Read / Update and the like, and `toolKind()` classifies the result summary. Unknown tools from a new tool show their raw name, with the summary falling back to "first 3 lines of output".
- `/clear` goes through `session.clear` (`Hub::clear`): chat mode only. It ends the tool process (invalidating the generation first), deletes all of the session's events and uploads, resets usage and context, and clears `external_id`, so the next message naturally starts a new tool session; the Yi Console session itself stays. Afterwards it persists an `EventBody::Cleared` (seq keeps counting); when the frontend's `addEvents` sees it, it drops earlier events, and reconnect catch-up relies on it too. usage_log isn't deleted, so the usage page still counts it. Typing `/clear` and pressing Enter in the input box is intercepted too and never sent to the tool.
- `/compact` goes through `session.compact`, equivalent to sending a `/compact` message. Codex's app-server doesn't understand `/` commands, so `start_turn` in `codex.rs` turns them into `thread/compact/start`, `review/start` (`/review`) and a prompt that generates AGENTS.md (`/init`); the command list is in `slash_commands()`, and same-named commands from the tool are deduplicated in the menu.
- "Continue with another tool" (session menu; chat-mode sessions with an `external_id`, and terminal-mode sessions of every tool except Cursor; blocked when opened if there are no user messages): `session.logFile` returns the tool's own session log for tool + `external_id` (`history::session_file`: jsonl for Claude / Codex / Qoder / CodeBuddy, `~/.kiro/sessions/cli/<id>.jsonl` for Kiro). In terminal mode `session.logFile` first runs `guess_terminal_session` (so the id is the session the process is on now) and takes `hasUser` from the tool's log (`history::has_user`), since messages typed into the terminal aren't in our events; with no log found it says it can't tell rather than exporting. Cursor's ACP sessions have no readable file, so the frontend saves the "Export Markdown" content into the original session's upload directory via `session.attachFile`. Then the new session dialog opens (`newSession.handoff`: the original tool and shell can't be picked, chat mode is fixed, the host can't change), and the first message is generated from the template in `app/src/handoff.ts`, which only asks the new tool to read the log and report back, not to continue the work. The template can be edited in system settings (`HandoffCard.tsx`, stored in localStorage `handoff-template`; empty means default, which follows the UI language). Placeholders are `{tool}` `{title}` `{cwd}` `{path}` `{format}`; update `HANDOFF_VARS` when adding one. Notes on each tool's log format are in `formatHint()`.
- Compaction progress always uses `EventBody::Compact` (phase start/done/failed, trigger auto/manual, tokens before/after, duration): Claude's comes from compacting and compact_result in `system/status` plus `compact_boundary`; Codex's from item/started and completed of `contextCompaction` (manual or not depends on whether it was our `thread/compact/start`; no duration is reported, so the frontend computes it from timestamps); Kiro's from `_kiro.dev/compaction/status` (started / completed / failed, in `acp.rs`). Kiro's /compact turn ends at once and the compaction runs afterwards with the session idle; a prompt sent during it is never answered, so `acp.rs` holds messages in its queue until the status arrives. The frontend replaces "compacting" with the result in place, and Claude / Codex sessions don't show the "/compact" user bubble; Cursor has no compaction events, and Cursor and Kiro keep the bubble.
- Tool summaries in the chat must handle every tool's format: Cursor's results are JSON (possibly wrapped in another string), Kiro's are wrapped in `{"items":[{"Json"|"Text":…}]}`, and failed commands only return `exit code: N`. All of this is handled in `parseOutput` in `ChatView.tsx`.
- On Windows, when `YI_CONSOLE_HOME` is set, the named pipe name includes a hash of the data directory (`paths::pipe_name`), so isolated tests don't connect to the daemon in real use.
- Single daemon instance: `serve` binds first (`transport::bind`) and only then opens the database and runs `restore` / relay / resume timers, so an accidental second daemon (concurrent bridges, login autostart) exits without touching data. Windows relies on `first_pipe_instance`; Unix holds an flock on `yi-agentd.lock` for the process lifetime, and only the holder may delete / recreate the socket (a failed connect alone doesn't prove the socket is stale). The socket is removed in `Listener`'s Drop, while the lock is still held. On Windows `spawn_detached` starts the daemon via WMI, which doesn't inherit our environment, so it passes `--home <dir>` when `YI_CONSOLE_HOME` is set; `main` turns it back into the env var before anything else.
- The UI theme is in `app/src/theme.ts`: choosing light / dark sets `data-theme` on `<html>`. Dark variables in styles.css must be written twice: `@media (prefers-color-scheme: dark) { :root:not([data-theme='light']) … }` and `:root[data-theme='dark'] …`. In JS, check for dark with `isAppDark()`, not matchMedia directly.
- Scrollbars: one global rule at the top of `styles.css` (`::-webkit-scrollbar`: 4px rounded slider inside an 8px bar, colors from `--sb-thumb*`), desktop pointers only. The slider is hidden until the element scrolls: `scrollbars.ts` sets `data-scrolling` on the scrolling element for 800ms (a `:hover` rule doesn't work, Chromium doesn't repaint scrollbars on hover); the tmux scrollbar in `TerminalView.tsx` does the same with a `scrolling` class. Tweak colors per area by overriding `--sb-thumb*` (the terminal does); don't use `scrollbar-width` / `scrollbar-color` except `none` to hide, since in Chromium they override the webkit styles. Playwright headless hides scrollbars by default; pass `ignoreDefaultArgs: ['--hide-scrollbars']` to see them in screenshots.
- The UI font stack starts with `system-ui`, which lands on Microsoft YaHei UI on Chinese Windows. Don't bundle web fonts.
- Font sizes are per-device preferences in `app/src/fontPrefs.ts` (localStorage `ui-font`), split like VS Code's chat / editor font sizes: the chat size sets `--fs-body` / `--fs-chat` / `--fs-input` / `--fs-code` (replies in both styles, headings, user bubbles, input box, code blocks), the editor size sets `--fs-editor` / `--lh-editor` (CodeMirror, `MergeDiff`, `PaneDiff`, Markdown preview). New text in those areas must use these variables (or offsets from them), not fixed px; 0 means the stylesheet default. UI zoom is the desktop app's page zoom (`getCurrentWebview().setZoom`, 1.2× per step like VS Code, Ctrl/Cmd + = / - / 0, needs `core:webview:allow-set-webview-zoom`); the browser build and phones keep their own zoom.
- Sidebar styles: the "Sidebar" section at the end of `styles.css` overrides everything in one place: width 244px, row height `--side-row-h` 32px, font size `--fs-side` 13px, text about 14px from the left. Change the sidebar there, not with scattered rules earlier. Structure is host header → directory subheading → session rows. Host-related entries (history, files, terminal, usage, host settings) all live in the host row's "…" / context menu (`hostMenu`); don't add buttons to the list. Session rows are the tool icon in its own color + grey title (darker on hover / selection) + time on the right; only running / awaiting approval / errored replace the time with a status. The sidebar scroll area shows no scrollbar. The filter box doubles as the entry to message search (Enter jumps to the search page). Ended sessions (exited / error) idle longer than the threshold fold behind a muted "Show more (N)" row at the end of their own directory (not a host-wide bucket; text in the title column, becomes "Show less" at the end once expanded, as in Codex / ChatGPT); pinned sessions and search results never fold. Layout (by directory / by time) and the threshold (1–30 days or never, default 3) are device prefs in localStorage `side-prefs` (`sidePrefs` / `useSidePrefs` in `Sidebar.tsx`), layout toggles with the clock / folder button in the host header (not in a menu, so it is one click), threshold is set in Preferences. In the by-directory layout the host header also has a fold-all / unfold-all button (folds every directory while any is open; writes the same `fold-dirs-<host>` list as folding a single directory).
- New sessions remember, per tool, the last UI (chat / terminal), permission mode, model and thinking level (localStorage `new-session-prefs`, `NewSession.tsx`) and restore them when switching tools; remembered values the current tool or model doesn't support fall back to defaults.
- Which permission modes each tool supports is decided by `permission_modes(tool, mode)` in `hub.rs`, and `permModes` in the frontend's `NewSession.tsx` is kept in sync by hand; the UI only lists modes the current tool supports. Modes reported back by the tool that we don't know (such as Claude's `dontAsk`) are recorded and shown by their raw name, never dropped.
- Background tasks (`SessionInfo.background_tasks`, memory only) currently exist only for Claude: the `background_tasks_changed` list in stream-json is authoritative, output files are parsed from the tool_result text of background commands, `task_notification` leaves a line in the chat, and stopping goes through the `stop_task` control request. After a task ends, Claude starts a turn by itself (only `system/init`, no user message), which the adapter uses to switch the state back to running.
- Task lists are assembled in the frontend by `PlanTracker` in `app/src/plan.ts`: Claude `TodoWrite`, Codex `turn/plan/updated` and ACP `plan` are turned into `plan` events by yi-agentd and used directly; Kiro's `todo_list` tool (the result is the full list, only done / not done, cleared once everything is done, in which case the previous list is reused with everything checked) and newer Claude's `TaskCreate` / `TaskUpdate` (numbers taken from the `Task #N created successfully` result) are parsed from tool calls in the frontend, and those tool calls themselves aren't shown in the timeline (except failed ones). The timeline keeps only the latest card, collapsed into one line once everything is done; while tasks remain unfinished, a progress bar shows above the input box (`PlanDock.tsx`). Kiro has no "in progress", so while a turn runs the first unfinished task counts as in progress.
- The session page's "workspace files" (`FilePanel.tsx`): with no file open it's a single tree column (`.file-panel.browse`, width `--tree-w`); opening a file widens it (`--panel-w`), with the editor on the left (tabs for opened files above it) and the tree on the right. The chat area keeps at least 420px, and the session header and input box collapse their text when narrow via container queries on `.session-view`. The tree marks changes (M / U / D) from `git.changes` (with `diff: false`, statuses only, because running git diff per file is too slow in big repos). Line counts `added` / `deleted` aren't affected by `diff: false`: tracked files are computed in one `git diff HEAD --numstat`, new files have their lines counted (null for binaries and files over 200KB). The Changes view shows +N −M to the right of each file and as a total at the top, and the diff of a single file is fetched with `paths` when it's opened. Opened diffs (working tree vs HEAD, a commit vs its first parent, comparing two files) are full-file diffs like VS Code's (`MergeDiff.tsx`, `@codemirror/merge`: side by side or stacked, syntax highlighting, character-level marks, unchanged regions collapsed by default, which VS Code doesn't do): both sides come from `git.blob` (`<rev>:<path>`, 1 MB limit like `fs.read`) and the working-tree side is the editor's draft, so unsaved edits show. Binary, oversized or unreadable sides, older daemons without `git.blob`, and tool snippets outside git fall back to the hunk-only `PaneDiff`. Before git status comes back, don't use the snippets recorded by tools in the session as a diff. Like VS Code's Source Control view, the last git status per host + directory is cached in memory (`gitCache` in `FilePanel.tsx`): a remounted panel shows it at once and refreshes quietly (the root path and top-level listing are cached the same way in `rootCache`, since the Changes list and the tree are laid out against the root); the commit history caches its first page and each commit's file list (`logCache` / `showCache` in `GitHistory.tsx`) and doesn't wait for git status (it only hides once status says the folder isn't a repo). The Changes view lists only changed files, and an opened file can switch between "File / Changes" to see the diff. Content search goes through `fs.grep` (file-by-file in Rust with the `regex` crate, no rg dependency; literal unless `regex`, plus `include` / `exclude` comma-separated globs with VS Code's semantics in `glob_set`, and `paths` for open files only). Replace follows VS Code's search view (`GrepPanel.tsx`): `fs.replace` shares `Matcher` with `fs.grep` so both see the same matches, replaces only the listed results (line + column), skips files whose `stat` from the search no longer matches, keeps every byte outside the matches, and returns the old text for one-step undo (written back with `fs.write`'s conflict check); the open file with unsaved edits is replaced in its draft via `dryRun` + `content`; uploads use `fs.upload`, downloads and PDFs use `fs.read` with `raw: true` (all limited to 50MB); `fs.open` (open with the system program / reveal in file manager) only accepts local connections, and the frontend only offers it for the local host. On Windows, `fs.list` must strip the `\\?\` prefix canonicalize adds (`fsapi::strip_verbatim`) before building child paths, otherwise child paths don't match the root and git paths (a "?" in the breadcrumbs, git marks lost); the frontend's `unverbatim` handles old records. The outline is `app/src/outline.ts` using per-extension regexes, no syntax tree. Markdown preview is `MdPreview` in `FilePreview.tsx`: it renders top-level blocks with an `<a class="md-ln" data-line>` anchor before each, and both split-view scroll sync and outline jumps interpolate between anchors; relative-path images become `data-src` and are fetched via `fs.read`. "View changes" is no longer a separate page: `SessionActions.showChanges` sends `OPEN_CHANGES`, the session page opens the file panel on "Changes"; the panel doesn't offer commit / discard for now (yi-agentd's `git.commit` and `git.discard` are kept). Browser tabs are in `Browser.tsx`, with tab keys `web:<url>` (`web:file:<absolute path>` is an HTML file on the host), stored in tabs like any other tab; remote localhost URLs go through `ports.forward` first. HTML previews go through `ClientHub::serve_preview`: `preview.root` exchanges a directory for a random token, and both the Tauri custom protocol `ahfs` and yi-web's `/fsv/<token>/<relative path>` map to `fs.read` raw, reading only the token's directory (.. rejected). The preview iframe has no allow-same-origin, and external URLs may not share the app's origin, so pages can't reach `hub_call`. The Tauri window has `dragDropEnabled` off so HTML drag-and-drop gets system files. The editor is CodeMirror 6 (`CodeEditor.tsx`; folding, auto-closed brackets and VS Code's multi-cursor bindings). CodeMirror joins lines with `\n`, so the editor writes the draft back with the file's own line ending, and indentation is detected per file (`app/src/textFormat.ts`); `fs.read` flags files that aren't valid UTF-8 (`notUtf8`) and those open read-only, since saving the lossy text would corrupt them. Language packs are lazy-loaded by file name through `@codemirror/language-data`, and highlight colors come from `--hl-*` variables on `.file-panel`. The filter box uses `fs.search`; images are fetched as base64 with `fs.read` and `image: true`. Writing files goes through `fs.write`: saving sends the `modified` seen at read time, and if the agent changed the file meanwhile the write is refused and the user chooses between reloading from disk and overwriting; `fs.delete` only deletes files and empty folders. When a turn ends the tree refreshes, and open files without local edits are reread. Expanded folders are stored in localStorage `wp-exp-<host>/<cwd>` (missing ones are dropped quietly), and the tree takes VS Code's keyboard bindings (arrows, Home/End, Enter, F2, Delete) on a focus cursor separate from the open file; renaming a folder moves open tabs and expanded folders inside it. Open tabs and the current file are stored in localStorage `wp-open-<host>/<cwd>` and restored once the panel mounts and has the root (unreadable files are silently dropped). Double-clicking the empty tab bar or the empty editor area opens an untitled tab like VS Code's (`untitled:Untitled-N`, titled by its first line): its text lives only in memory (`untitledCache`, per panel key, so it survives remounts but not an app restart, unlike VS Code's hot exit), and saving asks for a path relative to the root (or absolute), writes with `createOnly` and asks before overwriting. "Add to chat" sends an `INSERT_COMPOSER` event, and the Composer appends `@relative-path` to the draft.
- Files sessions (`ToolKind::Files`, `"files"`) never start a process: `Hub::create` saves them as idle and returns (no prompt, no `external_id`), `restore` keeps them idle, `launch` / `send` / `set_mode` / `clear` refuse and `resume` is a no-op; check `ToolKind::has_process()` wherever a process would start. `tools::detect` always reports them available. The session page renders `FilePanel` with `standalone` (fills the page, no close / full screen / "Add to chat"; tabs keyed `wp-open-s-<host>/<session>` so several Files sessions in one directory keep their own tabs) plus the bottom terminal panel; the session menu is the short `filesMenu` in `SessionActions.ts`. The file panel is shared, so new panel features show up there too.
- The terminal button at the top right of the session page opens the bottom terminal panel (`TermPanel.tsx`); several can be open, switched with tabs, and the top edge drags to resize. The panel toggle is remembered per session (localStorage `term-panel-<host>/<session>`); don't change it back to a global toggle. The right-side file panel toggle is also per session (`file-panel-<host>::<session>`). Each terminal is a shell session whose `SessionInfo.parent_id` points at the chat session: the sidebar, overview and command palette all filter out sessions with a `parentId`, and `Hub::delete` deletes them along with the chat.
- Sending while the AI is replying (`session.send` with `queue: true`): Claude and Codex get the message directly (written to stdin for Claude, `turn/steer` for Codex) and read it after their next tool call; anything that misses that is handled by the tool after the turn ends. If Codex's turn ends just as we steer (steer errors), a new turn is started instead. Cursor, Kiro, and cases where the process must restart at turn end still queue in the hub.
- Automatic continue after a usage limit (chat mode, Claude / Codex; `DaemonSettings.auto_resume`, on if unset): the adapter emits `adapters::limit_hit(resets_at, limit)` before `TurnEnd` (Claude from `rate_limit_event` with `status: rejected`, Codex from `codexErrorInfo: usageLimitExceeded` plus the full window in `account/rateLimits/updated`; `is_usage_limit_text` is the text fallback). Other tools only need to emit the same event. In `hub.rs`, `limit_hit` uses the reset time or asks `probe::quota`, then `plan_resume` stores `SessionInfo.auto_resume` (persisted; `arm_pending_resumes` re-arms after a daemon restart) and a timer sends `CONTINUE_ZH` / `CONTINUE_EN` (language from `settings.uiLang`, which clients report on connect and on language change) one minute after the reset. Every step is a `RateLimit` event (hit / scheduled / skipped / resumed / cancelled). Sending a message by hand, `/clear` and switching mode cancel it; queued messages are held after a limited turn; more than `MAX_AUTO_RESUMES` hits in a row, or a reset more than a day out, isn't waited for. The frontend shows one line per episode in the timeline, a countdown bar with "Continue now" / "Cancel" above the input box (`LimitDock.tsx`, `session.autoResume`), and the time in the sidebar row; wording is in `app/src/limit.ts`. The turn-end notification for a limited turn has kind `rate_limit` and is worded by the client.
- Questions from the AI go the same way as approvals: `PermissionRequest` carries `questions`, the options are fixed to `answer` / `skip` (kind isn't allow/reject, so phone notifications show no buttons), `session.permission` answers with `answers`, and `PermissionResolved` records them. For Claude it's AskUserQuestion inside `can_use_tool` (answers go into `updatedInput.answers`, keyed by the question text); for Codex it's `item/tool/requestUserInput` (only appears in Codex's plan collaboration mode); for Cursor it's the extension request `cursor/ask_question` (choose only, no free text; when the client doesn't support it Cursor falls back to one request_permission per question, and whether the model gets this tool is decided by Cursor's server). Kiro has no question tool, so the frontend recognizes "numbered questions + a) b) options" in the last reply and sends the answers as a `1=a, 2=b` message.
- Reply display style (system settings "Chat appearance" or the toggle at the top right of the session page, stored in localStorage `chat-style`): the default "compact" groups adjacent thinking and tool calls under a one-line summary title, expanded while running; "Claude Code" is the original dot timeline.
- Cursor's ACP doesn't report token usage or context: the context ratio is read at turn end (and on resume) from `~/.cursor/chats/<md5(cwd)>/<session id>/store.db`, where field 5 of the root record pointed to by latestRootBlobId in meta is token_details {1 used, 2 max}; per-turn token usage isn't available.
- Coding tools in terminal mode continue their original session on restart: Claude pins the id with `--session-id` on first launch (recorded as `external_id`; if it exits without anything said, the next launch starts a new one with the same id); Codex, Cursor and Kiro can't be given an id at launch, so `Hub::guess_terminal_session` works it out before `session.resume`, before switching to chat, before a hand-off, and every minute for running sessions (`track_terminal_sessions`). It matches the session's own process runs (`SessionRt.runs`, memory only): Codex by the rollout's `session_meta.timestamp` falling inside a run (`codex_owners`; only `source: cli`; a fresh TUI creates its session 2-4 s after launch, `codex resume` runs create none; two launches in one directory within the window stay unassigned rather than guessed), Kiro by the pid in `~/.kiro/sessions/cli/<id>.lock`, which is the `kiro-cli acp` grandchild the pty adapter samples from the process tree (`proctree::descendants`, `tmux::pane_pid` under tmux; `kiro_owned`). Both follow a newer session the same process opens (Codex `/new`). Cursor, and sessions whose runs were before a daemon restart, fall back to the newest session in the same directory used since the session was created and not claimed by another one (`newest_in_dir`), only while no id is recorded. Kiro's `<id>.json` says `session_created_reason: subagent` even for the main chat, so don't filter on it.
- Qoder (`qodercli --acp`) and CodeBuddy (`codebuddy --acp`) go through `acp.rs`; the arguments for entering ACP are in `acp_arg`. Both are Claude Code look-alikes: in terminal mode, like Claude, they pin the id with `--session-id` on first launch (`history::pins_session_id`), and session files are `<id>.jsonl` under `~/.qoder/projects` and `~/.codebuddy/projects` (`tool_session_exists` decides whether `--resume` works). Qoder's jsonl is Claude's format, so the history list and viewer reuse `scan_claude` / `read_claude`; CodeBuddy's is `{type:"message", role, content:[{input_text|output_text}]}`, only parsed for the list (`scan_codebuddy`), with content replayed by `session/load`. Qoder has no plan mode, and choosing "allow for this session" in its approvals switches it to acceptEdits, so auto-approval prefers `allow_once`. A failed CodeBuddy turn (e.g. not logged in) doesn't return a JSON-RPC error but `stopReason: refusal`, with the error in `_meta["codebuddy.ai/errorMessage"]` (`meta_error`); context usage comes from ACP's standard `usage_update` (with credits from `cost.amount`), while Qoder's context ratio comes from `context_usage_ratio` in the jsonl. Account quota (`probe.rs`): Qoder sends `get_usage_info` via `-p --no-session-persistence --input-format stream-json`; CodeBuddy gets a token from ACP's `_codebuddy.ai/getUserInfo` and then queries `get-user-resource-summary`. Empty sessions Qoder creates while probing models end up in its history, so they're deleted with `session/delete` afterwards.
- Android's `MainActivity` comes from `app/src-tauri/android/MainActivity.kt` in the repo (`gen/android` is generated and not checked in; CI copies it over after `tauri android init`, together with the launcher icons in `app/src-tauri/icons/android`, which would otherwise stay as whatever an earlier init left in `gen/android`). In edge-to-edge mode the system no longer shrinks the window for the IME, so it pads the bottom of the content by the IME inset (minus the navigation bar height the page already reserves via safe-area). The chat area's `ResizeObserver` keeps it pinned to the bottom when it gets shorter. The back key / back gesture is handed to the page's `window.__yiConsoleBack()` (`app/src/back.ts`): first close the topmost dialog, menu, image viewer or file / terminal panel registered with `useBack(active, close)`, then collapse the command palette and the left navigation (drawer, staying on the current page), then `goBack()`; when there's nothing left, first show "press again to exit", and only a second press within 2 s makes the page return false so the app calls `finish()`. Anything new that covers the page must register with `useBack`. QR pairing doesn't use a native plugin (Tauri's official barcode-scanner relies on ML Kit from Google Play services, which crashes on opening the camera on phones in mainland China); instead `QrScanner.tsx` uses `getUserMedia` + jsQR in the page. When the WebView needs the camera, wry requests CAMERA from the system, and the manifest permission is written into `gen/android` by `src-tauri/build.rs` during Android builds. On mobile, the "+" in the input box first asks "Photos" (`accept="image/*"`, opens the gallery) or "Files".
- Sidebar width: dragging `.side-resizer` in `Sidebar.tsx` writes `--side-w` on `.sidebar` (244–480px, localStorage `side-w`); desktop widths only.
- Tool badges (`ToolBadge`) use each tool's own logo (Claude Code uses claude.ai's starburst, Codex uses ChatGPT's OpenAI flower); shapes come from `@lobehub/icons` (MIT) and are inlined in `Icon.tsx`.
- The history page can be limited to one directory (`View.history.cwd`, including subdirectories), entered from a directory row's context menu in the sidebar.
- The main area and terminal containers use `overflow: clip` rather than `hidden`: hidden can still be scrolled by the browser, and when the terminal's hidden IME textarea sits at the right edge it pushes the whole session area left.
- Switching between chat and terminal mode goes through `session.setMode` (`Hub::set_mode`): first end the current process (invalidating the generation so the old process's exit events don't reach the session; programs in tmux are waited on until they really exit with `tmux::kill_and_wait`), then start the new mode continuing the same `external_id`. Switching to terminal records the number of user messages already in the tool session in `SessionInfo.synced_users`; switching back to chat imports only what came after: Claude / Codex read the tool log skipping the first N user messages (`after_users`), Cursor / Kiro let ACP replay and skip with `StartSpec.replay_skip`. Cursor's ACP sessions (`~/.cursor/acp-sessions/<id>`) and terminal UI sessions (`~/.cursor/chats/<md5(cwd)>/<id>`) are separate copies, so `history::cursor_handoff` copies store.db across when switching. Codex in terminal mode gets `--no-daemon` (`tools::codex_no_daemon` checks `--help` for support first); otherwise the session stays held by Codex's shared background service after exit, and chat mode fails to continue it with "already has an active writer".
- Cursor in terminal mode gets no `--model` (`interactive_args` in `pty.rs`): chat-mode (ACP) model ids carry parameters like `grok-4.7[reasoning_effort=high,fast=true]`, the interactive UI often reports "Cannot use this model" on Windows, and mapping to the names from `--list-models` would need another cursor-agent run (about 8 s on Windows). Without it, Cursor uses the last choice recorded in `~/.cursor/cli-config.json`.
- Local-only methods (`fs.open`, `proxy.setHosts`) are gated by the peer in `serve_conn`: local clients start `yi-agentd bridge --local`; `yi-agentd bridge` started over SSH has no `--local` and first sends a `BRIDGE_REMOTE_MARK` line after connecting, so the daemon records the connection as `ssh`. The marker line deliberately has no id, so older daemons ignore it as a bad request. Anyone who can SSH in as the same account can do anything anyway; this guards against Yi Console clients reaching these methods over SSH.
- Idle release is `Hub::release_idle` (run every minute from main), only for chat-mode sessions that have a tool session id and are idle.
- Clicks on `<a href>` in the page are intercepted by `guardLink` in `main.tsx`: external URLs open through `openUrl` (system browser on desktop; on the mobile app, the opener plugin's `inAppBrowser`, i.e. Android Custom Tabs), and relative paths etc. are blocked, so nothing navigates inside the app window. Right-click / long-press on a link is `linkMenu`: open, "open in another browser" on mobile (`openUrlExternal`, calling `YiConsoleAndroid.openExternal` injected by MainActivity to show the system chooser; http/https only), copy link. The mobile capability must include `opener:allow-default-urls`, otherwise you get "Not allowed to open url". Components that handle links themselves call `preventDefault`; download links carry the `download` attribute.
- The frontend no longer uses `prompt` / `confirm` / the browser context menu: use `askText`, `askConfirm` and `openMenu` from `components/Overlay.tsx`. Session actions live in `components/SessionActions.ts`, shared by the session page menu and the sidebar context menu.
- Terminal replay swallows terminal queries in the replayed history (the CSI hook in `TerminalView`), otherwise xterm.js's answers would be typed into the shell as keyboard input.
- Referencing files in the input box: "Copy" in the file panel writes the relative path to the clipboard and also remembers it in `copiedRef` in `FilePanel.tsx`; when the Composer pastes exactly that text, it becomes `@relative-path`. Non-image system files (`clipboardData.files` / drag-and-drop) go through `session.attachFile` (`hub::attach_file`, saved to `uploads/<session>/files/`, with spaces and illegal characters in file names replaced by `_` and a counter added on clashes) and are inserted as `@absolute-path`.
- Images are saved by yi-agentd to `<base>/uploads/<session id>/`; events only carry an `ImageRef` (id + mimeType), and the frontend fetches them on demand with `session.image`.
- Images in reply text (`![](…)`): `renderMarkdown` in `util.ts` doesn't output `<img>` but a `<span class="md-rimg" data-kind data-src>` placeholder, filled in by `hydrateImages` in `chatImages.ts` (`ChatView` provides the host and cwd via `ImgContext`). Files on the host (absolute, relative to cwd, `file://`) are read directly via `fs.read` with `image + strict` on the local host; remote hosts show a placeholder first, and on click `probe` gets the size and `askConfirm` confirms before downloading. Public URLs are always loaded by the current device only on click, so opening a chat never requests third parties. `strict` only accepts real images by file header, so a model referencing something like `~/.ssh/id_rsa` in a reply can't have it read out. In chat mode, Claude (`--append-system-prompt`) and Codex (`developerInstructions`, which overrides the same setting in config.toml) get `adapters::IMAGE_HINT`, telling the model to show images to the user as Markdown images with absolute paths; ACP tools have no system prompt entry point, so they don't get it.
- Forwarding through a computer (`yi-agentd/src/proxy.rs`): the desktop client syncs shareable SSH / relay hosts (`HostConfig.relay_share`, on by default) together with jump hosts and its own known_hosts to the local yi-agentd (`proxy.setHosts`, local connections only). A device connected to the computer through the relay discovers them with `proxy.list` and stores them as `HostKind::Proxy` (id `<relay host id>~<target id>`); when connecting, it opens a new relay connection whose first message is `proxy.connect`, after which the connection is passed through as is to the target yi-agentd. Forwarded hosts aren't auto-upgraded.
- Port forwarding: the yi-agentd side is `crates/yi-agentd/src/ports.rs` (`ports.list` lists listening ports; like `proxy.connect`, `port.connect` is the first message on a connection, after which bytes go as is to 127.0.0.1:port, loopback only). The client side is `crates/client/src/forward.rs` (listens on local 127.0.0.1 and calls `ClientHub::open_port` per connection: SSH uses direct-tcpip, falling back to exec `yi-agentd bridge` + `port.connect`; relay / forwarded hosts open a new connection and send `port.connect`). The commands are `ports.forward` / `ports.unforward` / `ports.forwards`, with `ports.changed` pushed on changes; `url.open` opens a URL in the system browser. Forwards live only in client memory and aren't persisted.
- yi-agentd only opens local IPC and never listens on TCP. Remote access goes through the SSH bridge or the relay; don't add network ports to yi-agentd.
- Relay (design in `docs/relay-security.en.md`): the protocol lives in `crates/link` (`auth.rs` relay-layer challenge signatures, `e2e.rs` Noise IK / IKpsk1, `wire.rs` connections and control messages), the relay server in `crates/relay`, and the yi-agentd side in `crates/yi-agentd/src/relay.rs`. URLs carry no keys; all authentication happens in the first messages after the WebSocket upgrade. Three kinds of links: `yiconsole://relay?v=2` (access link with a one-time invite code, for registering a computer with the relay), `yiconsole://pair?v=2` (pairing QR code: device public key + one-time pairing code), and `yiconsole://paired?v=2` (credentials the client stores in `HostConfig.pairing` after pairing, including the client private key). When `hosts.save` receives a pairing link it runs `client_pair` first and then stores the credentials. Changes to the handshake or message format must be made on all three sides, and `v` in the links must be bumped when old versions become incompatible.
- Relay auth failures come in two kinds (`deny` / `refuse` in `relay/src/hub.rs`): bad signatures, malformed messages, and guessing invite codes or pairing tickets count toward per-IP bans; a proven identity without permission (removed, device offline) doesn't, and clients that hit such a refusal (4403 / 4410 in `fatal_code`) also stop auto-reconnecting.
- Host configs sent to the frontend must go through `redact()` first, replacing passwords and private keys with `********`. If a save comes back with `********`, keep the original value.
- App self-update (`app/src/update.ts`, UI in `components/AppUpdate.tsx`): desktop uses tauri-plugin-updater behind the `update_check` / `update_install` commands (`app/src-tauri/src/updater.rs`); Android uses the `YiConsoleAndroid.updateCheck` / `updateDownload` bridge in `MainActivity.kt`, which answers through `window.__yiUpdate`, verifies the APK's sha256 and opens the system installer (`REQUEST_INSTALL_PACKAGES` is added by `src-tauri/build.rs`). Both read manifests from the latest GitHub release (`latest.json` / `latest-android.json`, written by `scripts/release-manifest.mjs`); the repository URL is in `tauri.conf.json` and `MainActivity.kt`. The version comes from the `v*` tag (`scripts/set-version.mjs` in CI), never edit it by hand. A failed check (no release yet, private repository, no network) counts as "no newer version", for manual checks too; only install errors are shown.
- The local daemon always runs from `~/.yi-console/bin/yi-agentd` (synced by `crates/client/src/localbin.rs`). Don't run the sidecar in the install directory directly, and don't register install-directory paths as the autostart service.
- The backend handles requests on the same connection concurrently, so input that must stay ordered (such as terminal keystrokes) has to be queued in the frontend; see `TerminalView.tsx`.
- Code comments are in English. The daemon's error messages are in Chinese (translated for the English UI by `app/src/i18n.ts`). UI text is bilingual Chinese/English via i18next: strings live in `app/src/locales/{zh,en}/<namespace>.json` (one namespace per source file, registered in `locales/index.ts`), and code does `const t = getT('<namespace>')` then `t('key', { name })` (named `tx` in files where `t` is already a local). Chinese is the primary language: its files define the keys, and `npm run i18n:check` (part of `npm run build`) regenerates `locales/resources.d.ts` so tsc rejects unknown keys and missing / misspelled `{{placeholders}}`, then runs `i18next-cli status` (en has every key) and `i18next-cli lint` (placeholders match between languages; new hardcoded JSX text fails, existing cases are in `i18next-lint-baseline.json`). Plurals use i18next's `key_one` / `key_other` with `count`. Don't build sentences by concatenating translations or template strings; give the whole sentence one key with placeholders. The language is stored in local localStorage `ui-lang` (follow system / Simplified Chinese / English) and switched in system settings; `useLang()` in `App` redraws the whole UI. Every new user-visible string needs both languages, not just Chinese: add the key to both JSON files. Text built inside `useMemo` must include the lang from `useLang()` in its dependencies, or it won't update when the language changes.
- Docs are bilingual: `X.md` is Chinese and `X.en.md` is English (README.md / README.en.md, docs/*.md / docs/*.en.md), each linking to the other at the top. When you change one, update the other in the same commit. AGENTS.md and CLAUDE.md are English only.

## Testing

```bash
cargo test
cargo build && (cd app && npm run build)
./target/debug/yi-web --listen 127.0.0.1:3001 --dist app/dist --token dev --yi-agentd-dir ./target/debug
```

For end-to-end tests, set `YI_CONSOLE_HOME=<temp dir>` so yi-agentd runs in an isolated environment and `~/.yi-console` is left alone.

Tauri and Android are only built in CI (`.github/workflows/build.yml`). Don't force a local build on machines that lack the webkit dependencies or enough memory.
