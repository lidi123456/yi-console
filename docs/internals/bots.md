# Bots

Always-on orchestrating sessions ("Bots") and the sessions they spawn ("tasks"). Design and later phases: [docs/proposals/bots.md](../proposals/bots.md). This file describes what is built (phases P1 to P4, then the form-less setup).

## Where things run

- The Bot engine and its plugins run only in the desktop app (`crates/bots`, crate `yi-bots`, started from `app/src-tauri/src/lib.rs` under `#[cfg(desktop)]`). Phones and yi-web are remote controls: `bots.*` / `tasks.*` / `connectors.*` are unknown to their own `ClientHub`, so `app/src/bots.ts` keeps `list` null, and they reach desktop apps through a host's daemon instead (see Remote control).
- A Bot session and its tasks are ordinary yi-agentd sessions on any host. They carry `SessionInfo.bot` (`BotLink`: botId, botName, role `bot` / `task`, taskId, clientId of the desktop app). Host session lists, the session-mode overview board, project cards and recent-directory suggestions exclude all sessions with `bot` (`isHostSession`: `!parentId && !bot`), so Bot and task sessions are shown only under the Bots section (including while filtering the sidebar) and on `BotBoard`, never under a host even when the owning desktop app is offline.
- Engine state lives in `<app data>/bots.db` (SQLite): bots, prompt revisions, plugin instances, plugin kv, trigger events (unique per instance + bot + key, so a replayed event is ignored), tasks, attention items, the outbox. Installed plugins are in `<app data>/plugins/<id>/`. The client id is in `<app data>/client-id`.

## Hooks into the client and yi-agentd

- `ClientHub` takes an `Extension` (`crates/client/src/ext.rs`): unknown commands from the frontend go to `Extension::call`, every host notification goes to `observe`, host status changes to `host_status`, and `clientMcp.call` notifications to `client_mcp`. `ClientHub::emit_event` sends `{type: ...}` events to the frontend (`bots.changed`, `bots.notify`, `bots.attention`; handled in `store.ts`).
- After `hello`, the client sends `client.hello` (client id, kind, name). yi-agentd keeps the connection per client id in `clientmcp::Clients`.
- Client MCP bridge: `session.create` / `session.setClientMcp` take `clientMcp: [{name, clientId, tools, offline}]`. The tool is launched with an MCP server `yi-agentd client-mcp --session --server --ticket-file` (like the computer-use proxy: one-time ticket plus peer pid check via `proxy_access`). The proxy answers `initialize` and `tools/list` from the stored tool list itself; `tools/call` is sent to the owning client as `clientMcp.call` and answered with `clientMcp.result` (5 min timeout). When the client is offline, a tool with an `offline` text returns that text (the engine uses it for `report` / `ack` / `handback`, marked with `[yi-bots:offline]`), any other tool returns an error. Claude gets `mcp__<name>__*` in its allow list.
- `session.create` / `session.setSystemPrompt` take `appendSystemPrompt`: Claude gets `--append-system-prompt`, Codex `developerInstructions`, ACP tools a `<system-reminder>` before the first prompt of a new tool session or after the prompt changed (`prompt_dirty`). The launch fingerprint covers client MCP and the prompt: a change relaunches an idle tool, or sets `restart_pending` while a turn runs.
- `session.send` takes `origin`, stored on the `UserMessage` (and on a queued message until it is sent). The engine sends everything it adds with `origin: bot-engine`: merged inbox messages (unless they are only the owner's own untagged words, e.g. a new Bot's role), follow-ups and `send_task` text (`<bot-message>`) to tasks. The chat (`EngineNote.tsx`) shows such a message, instead of the person's bubble, as a dashed card headed "Sent by the Bot" (so nobody takes it for something they typed) with a note per tagged block (event, report, routine, approval, owner, handback, follow-up, notes, bot-message) and the original behind a toggle in the header. The tags carry what the note needs as attributes (`<owner event=.. summary=..>`, `<approval kind=.. text=..>`), since their text is English for the AI.
- `git.worktreeAdd` / `git.worktreeRemove` (`gitops.rs`): worktrees go under `DaemonSettings.worktree_root` (default `<base>/worktrees`), as `<root>/<repo name>-<md5 of repo path, 8>/<name>` on branch `yi/<name>`. Remove only accepts paths under the root and keeps the branch.

## Remote control

- yi-agentd keeps the desktop apps that sent `client.hello` over a local connection (`clientmcp::Clients::desktops`; kind `desktop`). Any client of that daemon (a phone over the relay, yi-web, another desktop over SSH) can call `clients.list` and `client.call {clientId, cmd, args}`. The daemon only forwards `bots.*` / `tasks.*` / `connectors.*`, only to a local desktop, as a `client.call` notification; the desktop answers with `client.result` (the same pending-call table as `clientMcp.result`). `ClientHub::on_notify` only accepts `client.call` from its `local` host and only for commands its extension handles.
- Who may call: `serve_conn` refuses `client.call` from a local peer whose pid is unknown or descends from the daemon (`clientmcp::spawned_by_daemon`, a parent-process walk), so AI tools the daemon started can't drive Bots; it also refuses `client.hello` from such processes so they can't pose as a desktop. Remote peers come through the SSH bridge or the relay, which are already authenticated.
- Events: `ClientHub::emit_event` also sends every engine event to the local daemon as `client.event`; the daemon broadcasts it as a `client.event {clientId, event}` notification. `clients.changed` is broadcast when a local desktop registers or goes away.
- Frontend: a Bots "source" is `''` (this app) or `<hostId>|<clientId>` (a remote desktop, `remoteKey`). `refreshRemoteHost` lists the desktops of a host when it connects or sends `clients.changed`, skipping this app's own client id; `botCall(cmd, args, src)` goes through `rpc client.call` for remotes. Pages take the source from the `BotSource` context (`useBotCall`, `useBotSource`); views carry `src`. Host ids on a remote desktop are mapped with `mapHost`: its `local` is the host we reached it through, its host X is our `<host>~X` forward when we have it, else the session can't be opened here (`hostNotShared`). The details and plugin pages take host lists from `bots.hosts` (the desktop's `hosts.list`) for remote sources.

## Engine (`crates/bots/src/engine.rs`)

- `ensure_session` finds or creates the Bot session (default directory `~/.yi-console/bots/<id>` on the Bot's host) and keeps its link, client MCP (`yi_bot` tools) and system prompt current.
- Inbox: events and task reports are pushed into a per-Bot inbox and delivered as one merged message when the Bot session is idle. Follow-ups on a task's thread go to that task. Events from bot senders are filtered, and so is ambient chatter when `ambient` is `record` (the default): an event that isn't addressed to the Bot, from a sender not on the allow list, and not from a built-in source is stored as `filtered` without waking the Bot (it can still `read_thread`); `deliver` passes it on as before. This runs before the model, like dsh's fast path. `accept`: `off` drops plugin events, `observe` (default) lets the Bot only record what it would do (`spawn_task` / `reply` are recorded on the event, not carried out), `auto` starts tasks only for explicit events (`Engine::explicit`: addressed, from a person, and from an allow-listed sender or a built-in source); other events are recorded as observed. The event ids delivered in the current turn are kept (`BotRt.turn_events`, cleared when the session goes idle), so a `spawn_task` without `event_ids` in that turn is judged as being about them; only a turn the owner started by typing in the Bot session runs `spawn_task` unconditionally.
- Task tools: `task.tool` is the default and `task.tools` lists other tools the Bot may pick per task (`spawn_task.tool`, anything else is refused with the allowed list). The Environment section of the Bot prompt lists them; the owner's sections say which suits what. `task.model` / `task.effort` apply to the default tool only, the others start with their own default; the permission mode is shared and falls back to the tool's default where unsupported.
- Tasks: `spawn_task` takes `request` for a direct owner request: quoted as is when it stands alone, written out with every fact and decision when it came out of the conversation (setup answers, a confirmed plan); events are never restated. It picks a `mode` (`worktree`, `repo`, or `scratch`) and target directory: configured `workspaces` (optional, with optional `name` and `about`, matched by name/path/index) or `~/.yi-console/bots/<bot>/tasks/<task>` in `scratch` mode; ad-hoc `cwd` is accepted only in owner turns (event/routine turns are restricted by code to configured workspaces or `scratch`). `spawn_task` writes the task row, the events' `spawned` disposition and the requester's acknowledgement (`ack`, one sentence, an `ack:<task>` outbox reply to the first event's conversation when its plugin can reply) in one transaction (`Store::spawn`), then tries the reply once. The brief tells the task it was acknowledged, and the task's own `ack` tool then sends nothing; tasks spawned without `ack` acknowledge themselves as before. `task.computerUse` (default false; turning it on is in `sensitive_changes`) authorizes tasks to use Computer Use on demand when `spawn_task` passes `computer_use: true` (`list_hosts` reports `arch` and `computerUse`, and `check_draft` rejects `task.computerUse` when every target host is known unsupported). Then `try_start` checks `maxConcurrent`, `tasksPerDay`, and a per-host desktop mutex (`desktop_holder`: at most one computer-use task in `working` or `needsYou` per host across all Bots), then `start_task` prepares the directory (`git.worktreeAdd` in `worktree` mode falling back to `repo` on non-git dirs, direct cwd in `repo` mode, or `fs.mkdir` in `scratch` mode) and creates the session (`session.create` with `computerUse`) with the brief, the mode-tailored task prompt (`task_prompt_for` with `# Your environment`) and the `yi_task` tools. If the target host reports `desktopUnavailable` (locked / signed out), `park_desktop_unavailable` creates an idle task session with `spec.pendingBrief = true`, puts the task in `needsYou` (`blocked`), raises an attention item and reports to the Bot; clicking "Continue" (`tasks.continue`) or `send_task` / `attach` checks the desktop (`check_task_desktop_ready`, re-enabling `session.computerUse` after a daemon restart), sends any held `pendingBrief`, and moves the task back to `working`. Terminal task transitions (`done` / `failed` / `stopped`) call `session.computerUse {action: "stop"}` so the host closes an idle desktop driver immediately instead of waiting for `keepDays`. Task state: queued / working / needsYou / ready / failed / done / stopped. `tick` (every 30 s) fails tasks past their timeout and starts queued ones. When the owner types into a task session the frontend calls `tasks.manual` (`noteOwnerMessage`); "Hand back" clears it and tells the Bot.
- Reports: a task's `report` goes to the Bot as a `<report>` card (progress doesn't wake it), the summary cut at `REPORT_CHARS` (600) with the total length; `task_status` gives the full text. A turn that ends while the task is still `working` (not taken over or held) gets a fallback report, as in dsh: `task_updated` keeps per task whether the session is busy (`task_busy`: not idle / exited / error, or `backgroundTasks` / `queued` not empty, so Claude's background shells and subagents keep the turn open); on busy → settled, `turn_ended` takes the trailing assistant text of the session history (`final_text`: after the last tool call, user message or earlier turn end), stores it as `lastReport {state: waiting, auto: true}` and wakes the Bot with `<report state="waiting" auto="true">` (or a note that the task said nothing). The first update after the app starts only records the state. The Bot settles such a task with `close_task {task_id, result: done | failed, summary}` (working, blocked or ready tasks whose session isn't busy and that the owner hasn't taken over; `lastReport.by = bot`), or it stays working until its timeout. Ready ("to review"): the Bot relays the result and closes the task as done unless the owner should review it (changed code, a branch or PR, a decision of theirs); then it stays ready until the owner's "Mark done" or the Bot closes it on their word. Ready never times out and doesn't count against `maxConcurrent`; `list_tasks` includes it. `send_task` / `attach` to a ready task reopen it (`reopen`: back to working, `startedAt` reset so the timeout counts from then, its attention items resolved). The task prompt asks for a report before every turn end and no repeat of it in the final message.
- Context: at `compactAt` percent the engine calls `session.compact` on the Bot session; notes (`bots.saveNotes`, also written by the Bot through its tools) are attached after compaction and in a new session.
- After a host reconnects, `catch_up` scans task sessions' history for tool results carrying the offline mark and re-delivers those reports.
- Prompts (`prompt.rs`, English): shared + Bot or mode-aware task built-in text (`repo` read-only instructions, `worktree` delivery rules, `scratch` directory rules, `PLUGIN` for plugin tasks, and `# Your environment`), then the owner's three sections (role, communication, delivery). Task sessions get all three, as dsh's workers do, delivery last. The sections are written by the Bot: the CONFIG text tells it to rewrite what the owner says into specific rules (keeping every fact and constraint, adding none), sort them into the three sections and show the saved text, instead of saving the owner's words. The task WORK rules forbid writing outside the task directory and installing software or toolchains without the person's yes (report blocked with the commands, then run them on the host after the yes), and tell Windows tasks to write UTF-8. Saving a changed prompt adds a revision.
- `bots.events {id, before, limit, disposition}` pages back by time and can keep one disposition. `bots.stats {id, days}` counts events by disposition and tasks by state per local day (oldest first) and gives today's use of `tasksPerDay`.
- Commands that only read (`bots.list`, `bots.get`, `bots.events`, ...) must not call `changed()`: the frontend refetches `bots.list` on every `bots.changed`.

## Routines, approvals and cost guards

- Routines (`BotConfig.routines [{id, name, schedule, prompt, enabled}]`, five-field cron in local time): `normalize` keeps given ids and numbers the rest `r1`, `r2`, ...; `validate` parses the schedules. `tick` calls `schedule_routines`: the next time per routine is kept in `BotRt.routine_due` (memory) and worked out from now, so runs missed while the app was closed are skipped; a changed schedule recomputes it. `start_routine` records a `RoutineRun` (table `routine_runs`, the latest `RUNS_KEPT` = 20 per routine) and pushes `<routine run=".." name="..">prompt</routine>` with `Inbox.run`; `deliver` marks it running and keeps it in `BotRt.turn_runs`. The Bot closes it with the `yi_bot` tool `routine_done {run_id, result: done | nothing | failed, summary}`; a turn that ends without it closes it as done. A scheduled run while the previous one is open is recorded as skipped; "Run now" (`bots.runRoutine {botId, routineId}`) is refused then and when the Bot is paused. Runs left open by a closed app are failed at start, and any run open for `RUN_HOURS` (6) is failed by `tick`. `bots.routineRuns {botId, routineId?, limit}`; `bots.list` gives `lastRuns` (latest per routine id). Routines ignore active hours.
- Draft then approve (`BotConfig.approval {reply, write}`, both false for older Bots, both true from `bots.create`): only in `auto` and only in engine turns (`BotRt.engine_turn`: events, reports, routines; the owner typing in the Bot session is exempt). `reply` and plugin tool calls that aren't `readOnly` (`connector_call`, which takes an optional `summary` shown on the card) then become an `ApprovalRow` (table `approvals`: kind reply / tool, state pending / approved / rejected / expired) instead of running; the tool result tells the Bot not to retry. `draft` fills in what the card shows (`source`: the instance's name; `quoteFrom` / `quote`: the sender and text of the event a reply answers), sends a line to the notify channels (`notify_owner`, shared with `attention`) and emits `bots.approval`. `bots.approve {id, approve, text?}` saves the decision before carrying it out (so a second click can't send twice); a reply may come back edited. The outcome goes to the Bot as `<approval id state>`: approved wakes it (with the result), rejected and expired ride along with its next message. `tick` expires drafts after `APPROVAL_HOURS` (2). `bots.list` gives `approvals` (pending); they count toward the sidebar dot and pill (`needsYouCount`). `ApprovalCards` shows them under the Bot session bar and on the details page. Turning approval off is a sensitive change.
- Token reminder (`budget.tokensPerDay`, 0 = off; reminder only, nothing is paused): `count_tokens` runs on every `session.updated` of the Bot session and its tasks. A session's tokens are input + output + cache writes (cache reads are left out: they would swamp the number); the last total per session and the per-day sum live in `plugin_kv` under `bot:<id>` (`seen:<session>`, `tokens:<YYYY-MM-DD>`, `reminded`), deleted with the Bot. A lower total than last seen counts as a reset (`/clear`); an older session seen the first time starts from its current total, one created today counts in full. Past the limit the owner gets one low-urgency attention item a day. `bots.list` gives `tokensToday`, `bots.stats` `tokensToday` / `tokensPerDay`.
- Active hours (`activeHours {days: ISO weekdays, empty = every day; start, end: HH:MM}`, an end before the start spans midnight and belongs to the day it starts; `None` = always): plugin events outside them are stored with disposition `held` instead of being pushed. Built-in sources (cron, session events), task reports, routines and the owner aren't held. `tick` (`release_held`) delivers held events oldest first once the hours start or are removed.
- All four are in `tools::draft()` and set by talking to the Bot; the prompt has a Routines section (rules plus the list) and Policy lines for approval (auto only), active hours and the token reminder.

## SOPs, in-place upgrades and tiered memory

- SOPs (`BotConfig.sops [{id, name, when, how, askHuman, delivery, enabled}]`, optional `Routine.sopId`): `normalize` numbers missing ids `s1`, `s2`, ...; `validate` checks `when` / `how` and routine `sopId` references. `PromptRevision` snapshots both `prompt` sections and `sops` (legacy JSON rows without `sops` default to empty); `bots.promptRestore` restores both and clears any dangling `Routine.sopId`. `bot_prompt` lists a compact SOP directory; `task_prompt_for` injects only the single matched SOP (passed via `spawn_task.sop`, validated against enabled SOPs) at the very end so it takes precedence.
- SOP pre-review (`reviewing` state): when a task bound to an enabled SOP with non-empty `delivery` calls `report(state="ready")` and `spec.reviewCount < MAX_SOP_REVIEWS` (2), it enters `reviewing` (still `active()`, keeping its concurrency slot and desktop mutex, with no owner notification). The Bot receives `<report state="reviewing" sop="...">` and either calls `send_task` to silently bounce it back (`reviewCount += 1`), `accept_ready` to promote it to `ready` and notify the owner, or `close_task`. When the Bot's turn settles to `idle`, any remaining `turn_reviewing` task is promoted to `ready` automatically so it can never get stuck.
- In-place `repo` → `worktree` upgrade (`send_task {task_id, text, mode: "worktree"}`): runs atomically — `git.worktreeAdd`, then `session.create` (no `prompt`, with `handoffFrom: old_sid` and same `BotLink`), then `session.send` (`origin: bot-engine` with `<previous-phase>` carrying phase 1's `summary` / `details` / `question` / `options` / `answered` plus `<bot-message>`), rolling back the worktree/session on error before touching phase 1. On commit, the old session is recorded in `spec.priorSessions` (cleaned up in `clean_task` and `delete_bot`), `seen_seq` is reset to `0`, `task_busy` is cleared, phase 1 has `clientMcp` stripped and is interrupted (keeping history inspectable), and `bots.taskUpgraded` lets the frontend follow the new session automatically. `task_updated` ignores updates from superseded sessions (`t.session_id != sid`), and `noteOwnerMessage` checks `task.sessionId === s.id`.
- Decision cards (`tasks.answer {id, answer}`): `yi_task.report` accepts `options` (2–4 clickable choices), `details` (up to 4000 chars) and `learned` (up to 300 chars). `TaskQuestionCard` renders in `SessionBotBar` (folded in a priority deck under Bot sessions), `BotView` and `BotBoard` (deduplicated against `attention`). Desktop-locked `pendingBrief` tasks stay on `tasks.continue`. For `worktree` / `scratch` tasks, `tasks.answer` wakes the task directly; for `repo` tasks it validates the Bot is enabled, marks `lastReport.answered` immediately (preventing duplicate clicks), and wakes the Bot with `TurnTrust::Review` so it can upgrade in place, answer read-only, or close.
- Tiered memory (`bot_memories` table: `id, bot_id, scope, content, source, updated_at`; max 80 total / 40 per scope / 300 chars, exact dedupe, refuses silent eviction; deleted with the Bot): `scope` is `""` (global) or canonical `<host>:<cwd>` resolved via `BotConfig::find_workspace`. `TurnTrust` (`External < TaskReport < Review < Owner`, highest waking trust delivered first so external chatter cannot downgrade an owner review) enforces memory permissions in code and derives `source` (never accepted from the model): `External` turns cannot write or delete; `TaskReport` turns may only write memories for `turn_workspaces` and cannot delete `owner` entries; `Review` (approval edit with `ApprovalRow.original_text` / decision answer) and `Owner` turns may write global and workspace memories. Bot sessions keep `bot_prompt` static (preserving KV cache and avoiding CLI restarts) and attach `<memories>` on new/compacted sessions (`BotRt.memories_due`); tasks get global + matching workspace memories statically in `task_prompt_for` (capped at 6000 chars, subordinate to built-in/owner/SOP rules). Frontend commands: `bots.memories` (in `READS`), `bots.saveMemory`, `bots.deleteMemory`, and `connectors.outbox` supports optional `botId` filtering.

## Creating and configuring a Bot (no form)

- There is no settings form and no separate configuration assistant: a Bot is set up by talking to it. `BotView.tsx` only shows the configuration (read-only), prompt revisions, notes, stats and events, with open-session, pause / resume and delete.
- Creating: the new session page in Bot mode (`NewSessionParams.bot = {src}`, opened by the "+" of a Bots section through `newBot(src)`): host, directory, AI tool, permission mode and model as for a session, chat mode only, no attachments; the first message is the role. Hosts are this client's; `unmapHost` turns one into the id the source desktop uses (the reverse of `mapHost`; hosts it can't reach are not offered). `bots.create {host, cwd, tool, model?, effort?, permissionMode?, role}` saves a Bot with defaults (name from the start of the role, one workspace = that directory, the same tool / model / effort for tasks, `accept: observe`, `notify: [app]`, origin `create`), creates its session and pushes the role as an owner message (`Inbox.owner`), then the page opens the session.
- Onboarding: while a Bot has no triggers its prompt has a "Getting started" section (`prompt::onboarding`), modelled on dsh's SETUP: (1) without asking, rewrite the role (saved word for word by `bots.create`) into the sections, pick a short name and look up plugins, instances, hosts and workspaces; (2) ask what is still open one question per message, each with a recommended answer (event sources, what a missing plugin needs, workspaces, notify target, observe / auto, routines); answers are settings, not task requests; (3) send one plan and carry it out after the owner confirms. Whatever stays open keeps the defaults.
- Changing: the `yi_bot` tools `get_config` and `update_config {changes, instances?, reason}`, plus the lookups `list_hosts`, `list_tools`, `list_models` (`tools.models` on the host), `list_connectors`, `list_instances` (masked) (`tools::SETUP_TOOLS`, `Engine::setup_tool`). `changes` is a JSON merge patch over the current configuration (`merge_patch`: objects merge, arrays and values replace, null sets null); `id` and `promptRevision` are kept. Unknown keys are refused against `tools::draft()` (the full `BotConfig` schema; serde would ignore them, and the test `the_draft_schema_covers_every_config_field` fails when a field is added without the schema), then `check_draft` runs the save rules and checks hosts, the existing or `new:` instances named in triggers / notify / allow and the capability each use needs; new instances lose any `x-secret` value and must have their other required settings.
- Only on the owner's word: `update_config` is refused while `BotRt.engine_turn` is set. The engine sets it when it delivers a message (events, task reports) unless every waking item is an owner message, and clears it when the session goes idle; so a turn started by typing in the Bot session (or by `bots.create`'s role) may change the configuration, text from events can't.
- Sensitive changes wait (`sensitive_changes`): switching `accept` to `auto`, changing `allow`, a Bot / task permission mode, enabling `task.computerUse`, or turning `approval.reply` / `approval.write` off. The checked configuration is kept in `BotRt.pending` (memory only, one per Bot; lost on restart), `bots.list` shows it as `pendingChange {id, summary, items}`, `bots.confirm` toasts it, and `SessionBotBar` shows a card. `bots.confirmChange {botId, id, approve}` applies or drops it and tells the Bot as an `<owner>` message.
- Applying (`apply_config`, origin `bot`): new instances are created first through `Engine::save_instance`; one still missing a required setting (always a secret) is saved disabled (`validate_config(.., required: false)`) and the Bot points at it anyway. The `new:` refs become the new ids. After saving, `drop_unfinished` deletes instances the Bot stopped using that are disabled, still miss a required setting and no other Bot uses (e.g. a first attempt it replaced), so no half-made configuration is left behind. `bots.secretsNeeded {botId, name, pending: [{id, name, missing}]}` toasts a link to the Bot session (unless it is on screen), and the tool result tells the Bot which configurations wait for secrets and not to ask for them in the chat. Prompt changes add a revision the owner can restore (`bots.promptRestore {id, revision}`, origin `restore`).
- Secret cards (`secret_cards`, `bots.list` → `secrets`): for every instance a Bot uses (triggers, notify, allow) the required `x-secret` settings that are empty, plus the ones the Bot asked for with the `yi_bot` tool `request_secret {instance_id, fields?, reason}` (owner turns only; kept in `BotRt.secret_requests`, memory only, one per instance). Nothing else is stored: a card goes away once the value is there, wherever it was entered. `SecretCards` shows them in the session bar and on the details page as password fields; `bots.fillSecrets {botId, instanceId, values}` only takes the card's fields (an empty or masked value is skipped), saves through `save_instance`, enables the instance when the configuration is now complete, and tells the Bot as an owner message which keys were entered (never the values). `bots.dismissSecret {botId, id}` drops a request. They count toward `needsYouCount`.
- Plugins written by AI belong to the Bot but are built by a task: the Bot first asks the owner what the plugin depends on (cloud or self-hosted and the address, the kind of token, events, tools), then calls `spawn_task {kind: "plugin", request}`. A plugin task always runs in `scratch` (workspace / cwd / mode are ignored; `spec.kind`, `TaskRow::is_plugin`), its prompt gets the `PLUGIN` section (WASM component with our SDK only, connector_kit first, check Rust and `wasm32-wasip2` and ask before installing, fewest permissions, settings and secrets in the config schema, no notifications of its own, don't install or copy it out) and its brief points there. The task tool `connector_kit {dir?}` writes a cargo workspace (SDK, WIT, the testkit plugin as `example`, `GUIDE.md` = docs/connectors.en.md; all `include_str!` in `tools.rs`) on the task's host; `dir` is absolute or relative to the task's directory (`kit_dir`, default `yi-connector-kit`). When the task reports ready, the Bot checks it and calls `propose_connector {task_id, path}` (relative to the task's directory): the engine reads a `.yiconnector` or a folder (connector.json, the `main` component, prompt.md / README.md / LICENSE) from the task's host with `fs.read raw`, checks it like `plugins.inspect` and stages it; `bots.pluginProposal {token, id, host, sessionId}` opens the plugins page with `view.review` when the Bot session is on screen (otherwise a toast), which loads `plugins.staged {token}` into the permission review. Installing stays the owner's click.

## Plugins (`crates/bots/src/connectors/`)

- `PluginRuntime` → `Manifest`s and `start(plugin_id, host)` → `PluginInstance`. The built-in runtime has `cron` (5-field cron in local time; runs missed by more than 2 minutes are skipped), `session-events` (turn end / error / pending approval transitions of sessions that are not Bots' own or sub-agents) and `app-notify` (singleton instance `app`, not stored; listed first by `plugins.instances`). Deleting an instance also removes it from every Bot's triggers, notify targets and allow list.
- Config is a JSON schema; `x-secret` values are masked (`********`) before they leave the engine and kept on save when the mask comes back. Labels: `title` / `description` are Chinese, `x-en` holds English ones. `x-labels` names enum items either as `{zh: [...], en: [...]}` in enum order (built-ins) or as a value → label map with `x-en.x-labels` for English (packages). `x-ui`: `cron`, `textarea`, `host`, `checks`; a string array without `items.enum` is edited one item per line. Integers are `type: integer`.

### WASM plugins (`plugins/wasm.rs`, `plugins/package.rs`)

- The interface is the WIT world `connectors/wit/yi-connector.wit` (`yi:plugin@0.1.0`): imports `host` (config, emit, kv, log, health, now, http-fetch, ws-open/send/close, exec, set-timer/clear-timer), exports `plugin` (start, stop, on-timer, on-ws, reply, notify, read-context, tools, call-tool). `SUPPORTED_APIS` lists the `api` values a manifest may declare. Changing the WIT incompatibly means a new api version; keep old ones loadable.
- wasmtime with the component model. Every instance has its own thread and `Store`; the engine talks to it through a channel (`WasmInstance::ask` blocks, so the engine calls it inside `spawn_blocking`). Timers live in the store; the thread sleeps until the next one. WebSockets run on the tokio runtime and post their events back into the channel.
- Limits: `CALL_LIMIT` (5 s) of guest time per call via epoch interruption (host-call time such as HTTP is subtracted), `MEMORY_LIMIT` 64 MB. A trap ends only that instance: the pending call gets an error, health turns `error`, and the instance is re-created after a backoff (1 s doubling to 30 s, reset after 2 min healthy).
- Sandbox: WASI with nothing granted (no files, sockets, DNS, env). `http-fetch` / `ws-open` only reach hosts in `permissions.net` (exact names, or `*.x` for subdomains of x; http/https and ws/wss only); `exec` only runs commands listed in `permissions.exec` (60 s limit, no console window on Windows).
- Packages: a `.yiconnector` zip (one top-level directory allowed), a directory, a URL or base64 data. `plugins.inspect` unpacks and checks the manifest and the component (it must instantiate against our linker) and returns a token plus the permissions added relative to the installed version; nothing is written until `plugins.install {token}` (one use). Install writes to `.<id>.new` and swaps, then restarts the plugin's running instances. `plugins.uninstall {id, keepData}` without keepData deletes the plugin's instances with their kv and outbox rows and prunes them from Bots. `plugins.setEnabled` keeps a disabled list in kv (`_app` / `disabledPlugins`); disabled plugins' instances don't start.
- Reserved ids (`builtin::RESERVED`): built-in plugin ids plus `app` and `builtin`. Node plugins are rejected for now.
- Outbox: replies (the Bot's `reply` tool, `ack`) and notifications go through the `outbox` table keyed by an idempotency key the plugin also gets. A failed send is retried by `tick` (up to 8 attempts, 30 s doubling, max 1 h); a reply that finally fails raises an attention item. `SendResult::Gone` means the conversation no longer accepts replies and is not retried. `connectors.outbox` lists rows for the UI.
- Plugin tools: the Bot gets `connector_tools` / `connector_call` over instances it uses that have the `tools` capability; when the Bot is not in `auto` mode only tools marked `readOnly` run. `plugins.tools` / `plugins.callTool` let the owner list and try them by hand.
- First-party plugins and the SDK live in `plugins/` (a separate cargo workspace, excluded from the root one): `sdk` (crate `yi-connector`), `github`, `feishu` (long connection: hand-written protobuf frames in `frame.rs`), `testkit` (end-to-end tests) and `pack`. Build: `cargo build --release --target wasm32-wasip2 -p yi-connector-<id>`, then `cargo run -p yi-connector-pack -- <id>` writes `plugins/dist/<id>/` and `<id>-<version>.yiconnector`. Author guide: [docs/connectors.en.md](../plugins.en.md).
- Bundled plugins: `github` and `feishu` ship with the desktop app. `scripts/bundle-connectors.py` builds and packs them into `app/src-tauri/resources/plugins/<id>/` (CI runs it before `tauri build`; the Android config drops the resources), and the app passes `<resource dir>/plugins` to `yi_bots::start`. `Wasm::new` loads them in place first with `Manifest.bundled` set (never read from connector.json); an installed copy with the same id in `<app data>/plugins` is deleted at startup, its instances and data carry over since they are keyed by plugin id. Bundled plugins update with the app: staging a package with their id (`plugins.inspect`, `propose_connector`), installing and uninstalling them are refused; disabling works. yi-web takes `--bundled-plugins <dir>` (e.g. `plugins/dist`) for tests.

## Frontend

- `app/src/bots.ts`: list, types, `botCall`, `mapHost` / `unmapHost`. `components/BotsSection.tsx`: sidebar section, Bot and task menus, `newBot`, `SessionBotBar` under the session header (with the pending-change card and the drafts to approve). `BotView.tsx`: read-only details (`view.kind === 'bot'`); it reloads `bots.get` whenever the Bot's entry in `bots.list` changes. `ConnectorsView.tsx`: plugins and their instances (`'plugins'`): install (file / URL / path) with a permission review, enable / disable, uninstall (keeping or deleting data), per instance the outbox and the tool list. Strings are in the `bots` namespace.
- Desktop close: with any Bot enabled and `ClientSettings.closeToTray` on (default), closing the window hides it and shows a tray icon (`app/src-tauri/src/tray.rs`); quit from the tray menu.
- Wording: "任务 / task" now means a Bot's task. The agent's todo list is "待办 / To-dos", Claude's background commands are "后台命令", sub-agents are "子 agent".
- Details extras: prompt revision history ("Restore" saves an old revision as a new one through `bots.promptRestore`; "Changes" shows a line diff against the revision it was based on), an activity card (`bots.stats`: budget bar, 14-day chart), and the task bar's "Sources" menu (`tasks.events`, opens event links).
- `components/BotActivity.tsx`: the event log page (`view.kind === 'botEvents'`, filter by disposition, load more), the activity card and the prompt diff. `components/BotBoard.tsx`: the overview board's Bot view (toggle on the overview, kept in localStorage `yi-console-ov-bots`; shown once any source has a Bot): one card per Bot of every source, the ones needing you first, with attention items, active and ready tasks.
- `tasks.removeWorktree` kills the task session's process first (`session.kill`): on Windows a directory can't be deleted while a process runs in it.
- Cleanup of ended tasks (done / failed / stopped; never ready ones), in `tidy_tasks` on every `tick` while the task's session isn't busy: the worktree goes right after the end unless `git.changes` finds anything uncommitted (untracked files count), then it is marked `dirty` and kept; a failed removal is marked `error` (`drop_worktree`, no `--force`, the branch always stays). After `task.keepDays` (default 7, 0 = never) the session is deleted (`session.delete`, which in `Hub::delete` also removes a `scratch` task's directory under `~/.yi-console/bots/<bot>/tasks/<task>`), a worktree that is clean by then goes too, and the row gets `cleanedAt` (`untidy_tasks` selects rows without it); the task row, its result and events stay. `tasks.cleanup` does the same at once from the task menu and returns `worktreeKept`. `tasks.retry` clears `cleanedAt`.
- Deleting a Bot (`bots.delete`, `sessions: true` by default): pauses the Bot first, kills and removes clean task worktrees (keeping dirty ones with uncommitted changes and returning their paths in `worktreesKept`), deletes all task sessions and the Bot's own session (`Hub::delete` also removes the default `~/.yi-console/bots/<bot>` directory once no scratch task subdirectories remain), sweeps connected hosts for any orphaned sessions of that Bot, and deletes all its records in `bots.db` (including pending outbox retries). On startup and host reconnect (`host_status`), `prune_deleted_bot_sessions` deletes any sessions owned by this desktop app whose Bot id no longer exists in `bots.db`.

## Testing

- Unit tests: `cargo test -p yi-bots` (config, store, prompt layering, cron, tools, packages, manifests) and `clientmcp` tests in yi-agentd. `cargo test` in `plugins/` tests the plugins' pure logic natively (the host imports are stubs there).
- Runtime test with real components: build the plugins and pack them, then `YI_TEST_PLUGINS=<plugins/dist> cargo test -p yi-bots testkit_component` loads all three, and drives `testkit` against a mock HTTP server (events, reply, sandbox refusals, time-limit trap and restart). Without the variable the test is skipped.
- End to end without the desktop app: build yi-web with the testing-only feature, `cargo build -p yi-agentd -p yi-web --features yi-web/bots`, and run `yi-web --bots` with `YI_CONSOLE_HOME=<temp dir>` and its own `--data` dir. The engine then runs inside yi-web, so its WebSocket commands (`bots.save`, `rpc` `session.send`, `bots.list`, ...) and the browser UI can drive a real Bot. A run spawns real tool sessions and spends tokens.
- Routines and approvals end to end: create a Bot with `bots.create`, ask it in its session for a routine, active hours and a token reminder and check the config; "Run now" on the details page must end in a `done` / `nothing` run; then add a `cron` instance firing every minute whose text asks for a reply, switch the Bot to `auto` with that trigger, and a draft must appear (edit and approve it from the card); `bots.stats` must count tokens.
- New Bot flow end to end: with that yi-web, a browser on the new session page in Bot mode creates a Bot on a real Claude session; check that it renames itself, that a plain change (e.g. tasks per day) is saved directly and that `accept: auto` waits for the card in the session bar. The kit written by `connector_kit` should build with `cargo build --release --target wasm32-wasip2 -p yi-connector-example`.
- Remote control end to end: next to that yi-web, start a second yi-web without `--bots` on the same `YI_CONSOLE_HOME` (own port and `--data`); it plays the phone: `rpc clients.list` lists the first one, `rpc client.call` drives its engine, and its WebSocket receives the `client.event` notifications.
