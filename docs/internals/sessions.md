# Sessions

How sessions run in `crates/yi-agentd/src/hub.rs` and how the frontend shows them: turns, queueing, mode switching, `/clear` and `/compact`, usage limits, questions, task lists, attachments.

- `assistant_delta` and `thinking_delta` are transient events with seq 0 and are not persisted. At the end of a turn, the complete `assistant_message` / `thinking` is authoritative.
- Queue persistence: `Queued` keeps image refs, not data. Images are saved to the upload directory when a message is queued and read back by `send_queued`, and `sync_queue` writes the whole queue as JSON to the `queues` table on every change, so it survives daemon restarts. `restore` loads it held, keeping a reason saved before the restart, else `SessionInfo.queue_paused` = restart (the other reasons are interrupt, user via `session.queue` pause, and handoff; `set_queue_paused` saves the session). A chat session whose saved status was still running / waiting-permission / starting had its turn cut off with the process: `restore` sets `restart_interrupted` and emits `EventBody::Interrupted` (terminal sessions in tmux keep running, so they aren't marked). `session.interrupted` continue sends `RESTART_CONTINUE_*` (finish the cut-off task, don't redo finished work), and `session.queue` resume does the same first when the flag is set, so the queue follows after that turn; any message sent clears the flag, dismiss just drops it. `after_turn` sends nothing while held, except a "Send now" item, and an interrupted turn holds the rest with reason interrupt. `session.queue` resume releases the hold and, when the session is idle, sends the next one at once. The hold goes away with the last queued message. `/clear` and mode switches drop the queue. Frontend: `QueueList.tsx` (edit, drag to reorder, up button on phones, pause / resume / clear).
- Queued messages (`session.send` with `queue: true`) and permission mode switches live in `hub.rs`: when a turn ends, `Emitter::event` calls `after_turn()` to send the next message or restart the process. Adapters receiving `AdapterCmd::SetPermissionMode` should switch while running where possible; when they can't (Claude switching to allow-all), the hub restarts the process.
- Sending while the AI is replying (`session.send` with `queue: true`): Claude and Codex get the message directly (written to stdin for Claude, `turn/steer` for Codex) and read it after their next tool call; anything that misses that is handled by the tool after the turn ends. If Codex's turn ends just as we steer (steer errors), a new turn is started instead. Cursor, Kiro, and cases where the process must restart at turn end still queue in the hub.
- Switching between chat and terminal mode goes through `session.setMode` (`Hub::set_mode`): first end the current process (invalidating the generation so the old process's exit events don't reach the session; programs in tmux are waited on until they really exit with `tmux::kill_and_wait`), then start the new mode continuing the same `external_id`. Switching to terminal records the number of user messages already in the tool session in `SessionInfo.synced_users`; switching back to chat imports only what came after: Claude / Codex read the tool log skipping the first N user messages (`after_users`), Cursor / Kiro let ACP replay and skip with `StartSpec.replay_skip`. Cursor's ACP sessions (`~/.cursor/acp-sessions/<id>`) and terminal UI sessions (`~/.cursor/chats/<md5(cwd)>/<id>`) are separate copies, so `history::cursor_handoff` copies store.db across when switching. Codex in terminal mode gets `--no-daemon` (`tools::codex_no_daemon` checks `--help` for support first); otherwise the session stays held by Codex's shared background service after exit, and chat mode fails to continue it with "already has an active writer".
- Coding tools in terminal mode continue their original session on restart: Claude pins the id with `--session-id` on first launch (recorded as `external_id`; if it exits without anything said, the next launch starts a new one with the same id); Codex, Cursor and Kiro can't be given an id at launch, so `Hub::guess_terminal_session` works it out before `session.resume`, before switching to chat, before a hand-off, and every minute for running sessions (`track_terminal_sessions`). It matches the session's own process runs (`SessionRt.runs`, memory only): Codex by the rollout's `session_meta.timestamp` falling inside a run (`codex_owners`; only `source: cli`; a fresh TUI creates its session 2-4 s after launch, `codex resume` runs create none; two launches in one directory within the window stay unassigned rather than guessed), Kiro by the pid in `~/.kiro/sessions/cli/<id>.lock`, which is the `kiro-cli acp` grandchild the pty adapter samples from the process tree (`proctree::descendants`, `tmux::pane_pid` under tmux; `kiro_owned`). Both follow a newer session the same process opens (Codex `/new`). Cursor, and sessions whose runs were before a daemon restart, fall back to the newest session in the same directory used since the session was created and not claimed by another one (`newest_in_dir`), only while no id is recorded. Kiro's `<id>.json` says `session_created_reason: subagent` even for the main chat, so don't filter on it.
- `/clear` goes through `session.clear` (`Hub::clear`): chat mode only. It ends the tool process (invalidating the generation first), deletes all of the session's events and uploads, resets usage and context, and clears `external_id`, so the next message naturally starts a new tool session; the Yi Console session itself stays. Afterwards it persists an `EventBody::Cleared` (seq keeps counting); when the frontend's `addEvents` sees it, it drops earlier events, and reconnect catch-up relies on it too. usage_log isn't deleted, so the usage page still counts it. Typing `/clear` and pressing Enter in the input box is intercepted too and never sent to the tool.
- `/compact` goes through `session.compact`, equivalent to sending a `/compact` message. Codex's app-server doesn't understand `/` commands, so `start_turn` in `codex.rs` turns them into `thread/compact/start`, `review/start` (`/review`) and a prompt that generates AGENTS.md (`/init`); the command list is in `slash_commands()`, and same-named commands from the tool are deduplicated in the menu.
- Compaction progress always uses `EventBody::Compact` (phase start/done/failed, trigger auto/manual, tokens before/after, duration): Claude's comes from compacting and compact_result in `system/status` plus `compact_boundary`; Codex's from item/started and completed of `contextCompaction` (manual or not depends on whether it was our `thread/compact/start`; no duration is reported, so the frontend computes it from timestamps); Kiro's from `_kiro.dev/compaction/status` (started / completed / failed, in `acp.rs`); Antigravity's from `CHECKPOINT` steps in `transcript_full.jsonl` (`acp.rs`: a manual `/compact` on a non-empty transcript emits `start` and settles to `done` or `failed` at prompt end, auto-compaction `CHECKPOINT` steps emit `done` at prompt end or during `AgyWatch` wakeups, `memory_notice` is re-armed on completion, and bare `/compact` resets `contextPercent` to `0.0` so the summarizer's pre-compact `usage_update` doesn't linger or loop Bot auto-compact). Kiro's /compact turn ends at once and the compaction runs afterwards with the session idle; a prompt sent during it is never answered, so `acp.rs` holds messages in its queue until the status arrives. The frontend replaces "compacting" with the result in place, and Claude / Codex / Cursor / Antigravity sessions don't show the "/compact" user bubble; Kiro keeps it.
- Cursor's ACP has no compaction (its terminal UI's `/summarize` isn't exposed) and treats `/compact` as a plain prompt, so `acp.rs` emulates it (`cursor_compact_start`): the tool is asked for a summary of the conversation in the same session (the reply is hidden from the chat; `/compact <text>` adds instructions, and a pending account hand-off the hub put first goes into the summary), then `session/new` replaces the ACP session (new `external_id`, same model and parameters, appended system prompt sent again) and the summary goes to the hub's `pending_handoff` (`Emitter::pending_context`) as a `<yi-compact-summary>` block put before the next message. Messages sent meanwhile wait (`compacting`); a cancelled or failed summary keeps the old session and ends with Compact `failed`. The hub doesn't put a hand-off before other slash commands (it waits for the next real message).
- Automatic continue after a usage limit (chat mode, Claude / Codex / Antigravity; `DaemonSettings.auto_resume`, on if unset): the adapter emits `adapters::limit_hit(resets_at, limit)` before `TurnEnd` (Claude from `rate_limit_event` with `status: rejected`, Codex from `codexErrorInfo: usageLimitExceeded` plus the full window in `account/rateLimits/updated`; `is_usage_limit_text` is the text fallback; Antigravity from its "Individual quota reached … Resets in 4h9m8s" reply in `acp.rs`). Other tools only need to emit the same event. In `hub.rs`, `limit_hit` uses the reset time or asks `probe::quota`, then `plan_resume` stores `SessionInfo.auto_resume` (persisted; `arm_pending_resumes` re-arms after a daemon restart) and a timer sends `CONTINUE_ZH` / `CONTINUE_EN` (language from `settings.uiLang`, which clients report on connect and on language change) one minute after the reset. Every step is a `RateLimit` event (hit / scheduled / skipped / resumed / cancelled). Sending a message by hand, `/clear` and switching mode cancel it; queued messages are held after a limited turn; more than `MAX_AUTO_RESUMES` hits in a row, or a reset more than a day out, isn't waited for. The frontend shows one line per episode in the timeline, a countdown bar with "Continue now" / "Cancel" above the input box (`LimitDock.tsx`, `session.autoResume`), and the time in the sidebar row; wording is in `app/src/limit.ts`. The turn-end notification for a limited turn has kind `rate_limit` and is worded by the client.
- Questions from the AI go the same way as approvals: `PermissionRequest` carries `questions`, the options are fixed to `answer` / `skip` (kind isn't allow/reject, so phone notifications show no buttons), `session.permission` answers with `answers`, and `PermissionResolved` records them. For Claude it's AskUserQuestion inside `can_use_tool` (answers go into `updatedInput.answers`, keyed by the question text); for Codex it's `item/tool/requestUserInput` (only appears in Codex's plan collaboration mode); Codex models can also call `request_user_input_async`, which returns `{accepted:true}` at once and keeps the turn running (the model sleeps and polls while it waits): app-server sends it as an `agentMessage` with `delivery: "async"` and `questions: [{title, options}]`, which `item_events` turns into the usual `AssistantText` plus `EventBody::AsyncQuestion` (same id). It is not a pending request: status stays running and `pending_permissions` is untouched; the hub only sends a "在等你回答" notification while the turn is open. The frontend pins the unanswered one above the input box next to pending approvals (`openAsyncAsk`, same `QuestionCard`), sends the answer as an ordinary `session.send` with `queue: true` (so it is steered into the running turn, or starts a new one), and in the timeline replaces that reply with an answered card whose answer is read back from the first user message after it (`asyncAnswers`); skipping is remembered per session in localStorage; for Cursor it's the extension request `cursor/ask_question` (choose only, no free text; when the client doesn't support it Cursor falls back to one request_permission per question, and whether the model gets this tool is decided by Cursor's server); for Antigravity (`agy acp`), declaring `clientCapabilities.elicitation.form` causes `ask_question` to send ACP `elicitation/create` (`mode: "form"`, `qN` + `qN_other` properties for single/multi-select options and free-form "Other" answers, answered with `accept` / `decline` / `cancel`). Kiro has no question tool (checked against kiro-cli 2.35.1), so its questions are plain reply text; we don't try to recognize them.
- Background tasks (`SessionInfo.background_tasks`, memory only) come from Claude, and from Codex and Antigravity subagents / background tasks (details in tools.md). A deferred restart (`restart_pending`, from permission mode, MCP or account switches), idle release, tool updates and host-account swaps all wait while `background_tasks` is non-empty or an adapter wakeup watch (`SessionRt.watch_active`, e.g. Antigravity's `AgyWatch`) is still active, so emptying `background_tasks` as the last task finishes never kills the process before its reactive wakeup turn runs; `relaunch` also refreshes a pending `<yi-account-handoff>` digest so deferred account switches don't carry a stale mid-turn snapshot. At a turn end with tasks or a watch left it stays pending, and `Emitter::background_tasks` / `Emitter::watch_active` runs `restart_when_settled` only once both are clear with the session idle. For Claude: the `background_tasks_changed` list in stream-json is authoritative, output files are parsed from the tool_result text of background commands, `task_notification` leaves a line in the chat and drops that task from the list when it has ended (a resumed Claude reports tasks from the previous process only this way, with no `background_tasks_changed` after it), and stopping goes through the `stop_task` control request. After a task ends, Claude starts a turn by itself (only `system/init`, no user message), which the adapter uses to switch the state back to running. The list is saved with the session info, so `restore` clears it: the process that owned the tasks didn't survive the restart.
- Task lists are assembled in the frontend by `PlanTracker` in `app/src/plan.ts`: Claude `TodoWrite`, Codex `turn/plan/updated` and ACP `plan` are turned into `plan` events by yi-agentd and used directly; Kiro's `todo_list` tool (the result is the full list, only done / not done, cleared once everything is done, in which case the previous list is reused with everything checked) and newer Claude's `TaskCreate` / `TaskUpdate` (numbers taken from the `Task #N created successfully` result) are parsed from tool calls in the frontend, and those tool calls themselves aren't shown in the timeline (except failed ones). The timeline keeps only the latest card, collapsed into one line once everything is done; while tasks remain unfinished, a progress bar shows above the input box (`PlanDock.tsx`). Turn-scoped lists belong to the turn that last updated them. Once that turn ends, their bar goes away until the next update, and the card keeps showing what is left. Kiro has no "in progress", so while the list's own turn runs the first unfinished task counts as in progress.
- Qoder task lists come from the account’s `QODER_CONFIG_DIR/tasks/<externalId>/` (default `~/.qoder/tasks/`). Qoder can continue after an ACP prompt ends, so the adapter checks those files while the process is alive. Opening a saved session also reads the files when the adapter is absent. Snapshots are deduplicated, persisted and broadcast as session-scoped `plan` events. The progress bar stays visible with unfinished tasks while Qoder is alive, and the timeline keeps the latest snapshot for closed sessions. Qoder builds without task files use their ACP or tool-call task updates.
- Files sessions (`ToolKind::Files`, `"files"`) never start a process: `Hub::create` saves them as idle and returns (no prompt, no `external_id`), `restore` keeps them idle, `launch` / `send` / `set_mode` / `clear` refuse and `resume` is a no-op; check `ToolKind::has_process()` wherever a process would start. `tools::detect` always reports them available. The session page renders `FilePanel` with `standalone` (fills the page, no close / full screen / "Add to chat"; tabs keyed `wp-open-s-<host>/<session>` so several Files sessions in one directory keep their own tabs) plus the bottom terminal panel; the session menu is the short `filesMenu` in `SessionActions.ts`. The file panel is shared, so new panel features show up there too.
- Idle release is `Hub::release_idle` (run every minute from main), only for chat-mode sessions that have a tool session id and are idle.
- Full-session prompt index (`session.userMessages`): returns `Vec<UserMessageSummary>` (`seq`, `ts`, `text`, `images`, `origin`) directly from the SQLite `events` table in ascending `seq` order, transferred over `ClientHub`'s SSH bulk channel (`BULK_METHODS`). When a chat session opens with `hasMore: true`, `loadUserMessages` fetches the complete prompt list in the background (silently degrading to loaded events on older daemons that return unknown method) and tracks `clearSeq` so `/clear` resets it without letting in-flight responses leak pre-clear prompts. Jumping to an unloaded prompt calls `loadOlder(hostId, sid, targetSeq)` with an enlarged `limit` (`first - targetSeq + 80`, capped at 20,000) to fetch earlier history in one call.
- Referencing files and code/diff snippets in the input box: "Copy" in the file panel writes the relative path to the clipboard and also remembers it in `copiedRef` in `FilePanel.tsx`; when the Composer pastes exactly that text, it becomes `@relative-path`. Diff hunks and editor line selections added from `FilePanel` (`contextRefs.ts`, `ContextRefBar.tsx`) appear as compact pills (`path:from-to` with optional `+N −M`) above the input box (`draft-refs-<session>`). In chat mode, sending appends `<yi-context>` blocks so the AI receives the exact code or unified diff (including deleted lines), while `ChatView` and `QueueList` strip the blocks and render only clickable pills above the user bubble; in terminal mode, snippets are uploaded via `session.attachFile` and referenced as `@path`. Non-image system files (`clipboardData.files` / drag-and-drop) also go through `session.attachFile` (`hub::attach_file`, saved to `uploads/<session>/files/`, with spaces and illegal characters in file names replaced by `_` and a counter added on clashes) and are inserted as `@absolute-path`.
- Context pills (`ContextRefBar.tsx`) follow Cursor's look: `name (10-11)` with the line range muted, the × only on hover, and a hover card with the location and the first 12 lines (diff lines colored). On touch screens (`hover: none`) the × is always shown and there's no hover card.
- New session page (`NewSession.tsx`, view `{kind: 'new', ...NewSessionParams}`, opened with `openNewSession` in `store.ts`; there is no dialog any more): the input box for the first message is the page. Host, directory, tool and UI are chips above it (menus via `openMenu`), permission mode and model / thinking level sit in its bottom bar using the same `PermPicker` and `ModelMenu` as a session (`ModelPicker` is the session wrapper around `ModelMenu`). The directory menu lists localStorage `recent-dirs` (per host, newest first, up to 8; the older single `recent-cwd` is read as a fallback) and then the directories of that host's sessions. After creating, `replaceView` swaps the page for the session so Back skips it. Resume shows no input; Files shows only an Open button; for shell the input is the command. The first message may carry attachments: in chat mode images go in `session.create` `images` with the prompt; when there are other files (or any attachment in terminal mode) the session is created without a prompt, the files are uploaded with `uploadChunked` (`Composer.tsx`) and the message goes out with `session.send` with the `@path` references appended. If that fails after the session exists, the page still opens the session with the message left as its draft.
- First message in terminal mode: `session.create` `prompt` (and any `session.send` in terminal mode) reaches the pty adapter as `AdapterCmd::Send`, which holds it until the program is ready to be typed into (`input_ready` in `pty.rs`: output quiet for 1.5 s, or 20 s after launch) and then types it, as a bracketed paste when the program has turned that on (`ESC[?2004h` seen in its output, so multi-line text stays one message), followed by Enter 150 ms later. Raw keystrokes (`pty.input`) are never held.
- Images are saved by yi-agentd to `<base>/uploads/<session id>/`; events only carry an `ImageRef` (id + mimeType), and the frontend fetches them on demand with `session.image`.
- Continue with another tool from a usage limit: `LimitDock` (while an automatic continue is pending) and the latest limit line in the timeline (when none is) call `handoffSession(..., {limit: true})`, which adds the tools whose sessions on that host are waiting for a reset (not picked by default). Every hand-off, from the menu too, passes the original session id and its permission mode (kept if the new tool has it, else default). `session.create` with `handoffFrom` runs `Hub::hand_over` after the first message: `cancel_resume(.., "handoff")`, moves the queue and its images to the new session held with reason handoff (its first turn only reports back), and emits `EventBody::Handoff` in both sessions (`to` true in the original). The timeline shows each as a line with a button to the other session.
- "Continue with another tool" (session menu; chat-mode sessions with an `external_id`, and terminal-mode sessions of every tool except Cursor and Antigravity; blocked when opened if there are no user messages): `session.logFile` returns the tool's own session log for tool + `external_id` (`history::session_file`: jsonl for Claude / Codex / Qoder / CodeBuddy, `~/.kiro/sessions/cli/<id>.jsonl` for Kiro). In terminal mode `session.logFile` first runs `guess_terminal_session` (so the id is the session the process is on now) and takes `hasUser` from the tool's log (`history::has_user`), since messages typed into the terminal aren't in our events; with no log found it says it can't tell rather than exporting. Cursor's ACP sessions have no readable file, so the frontend saves the "Export Markdown" content into the original session's upload directory via `session.attachFile`. Then the new session page opens (`openNewSession` with `handoff`: the original tool and shell can't be picked, chat mode is fixed, the host can't change), and the first message is generated from the template in `app/src/handoff.ts`, which only asks the new tool to read the log and report back, not to continue the work. The template can be edited in system settings (`HandoffCard.tsx`, stored in localStorage `handoff-template`; empty means default, which follows the UI language). Placeholders are `{tool}` `{title}` `{cwd}` `{path}` `{format}`; update `HANDOFF_VARS` when adding one. Notes on each tool's log format are in `formatHint()`.

- Optional Windows Computer Use grants are per-session. Pause/interrupt release desktop control; stop, kill, clear and mode switch revoke it. Driver results and image references flow through emit. Grants reset after daemon restart; see [computer-use.md](computer-use.md).
- Overview fields on `SessionInfo`, so lists can show them without subscribing to the session. `pending` is the oldest waiting approval or question (`PendingBrief`: title, the concrete command or file path taken from the request input, the options; questions carry no detail or options and are answered on the session page). It follows `pending_permissions` and is cleared with it, and on daemon restart. `turn` is the current or last chat turn: `deliver` starts it (imported history on a mode switch starts none), tool calls inside it update `filesChanged` (distinct paths from `ToolCall.diffs`, no git) and `activity` (the latest tool call, one line), `rejected` keeps the last approval answered with a reject option (interrupt cancellations and skipped questions don't count), and `turn_end` or the process exiting sets `endedAt`. A tool call that only changes `activity` is not saved and is broadcast at most once per 5 s per session (`push_activity`, with one trailing broadcast so a long command still shows); every other change goes out as before.
- Process exit events preserve `SessionInfo.updatedAt`, including approval and background task cleanup, exit errors and interruptions recorded after daemon restart. The overview and the `session-events` Bot plugin use `lastProcessErrorAt` for the time of an abnormal exit, with `updatedAt` as a fallback for older daemons.
- Same-session account switching and automatic rate-limit failover (`session.create` optional `accountId`, `session.switchAccount`, `SessionInfo.accountId`/`accountLabel`, `EventBody::AccountSwitched`):
  - Manual switching and automatic rate-limit failover keep the same `SessionInfo.id`, timeline, cwd, uploads, and queues (`apply_account_switch` in `hub.rs`), never spawning a separate Yi Console session.
  - Level 1 (`Isolated` `Codex`/`Claude`/`Qoder` same-backend history): copies the rollout/`.jsonl` session file into the target profile (`copy_session_history_for_switch`) and preserves `external_id` (`native_resume`). Level 2 (cross-backend / `HostActive` / ACP): clears `external_id` and stores `<yi-account-handoff>` in `SessionRt.pending_handoff`, injected only into the delivered adapter prompt on the next turn without polluting persisted `UserMessage` events (`summary_injected`).
  - Automatic failover: when `limit_hit` fires while tool-level `autoFailover` is enabled and no busy other session blocks a `HostActive` swap (`has_busy_other_host_session`), the next eligible profile with `allowAutoFailover: true` (`priority` desc) is recorded in `pending_failover`; at `after_turn` the hub switches the session in place, marks the limited profile `Limited`, and sends the continue turn on the new profile (or falls back to timer `auto_resume` if no eligible backup exists). A clean non-limit turn clears `failover_tried` and restores `Ready`. Changing a `HostActive` tool's active profile (`tools.accounts.activate`) syncs existing idle host-bound sessions via `on_host_account_activated`.
- Turn-level hidden git checkpoints (`SessionInfo.checkpoints`, `git.refDiff`):
  - Before delivering a structured top-level prompt in a git repository, `deliver()` captures a hidden ref `refs/yi/checkpoints/<sid>/t<N>-base` via a temporary `GIT_INDEX_FILE` (including non-ignored untracked files, capped at 2,000 files / 50 MiB, leaving `.git/index` untouched). On `TurnEnd` (before `after_turn()`), `finalize_turn_checkpoint` captures `t<N>-end` and computes exact `(filesChanged, added, deleted)` stats; turns with no file changes immediately delete both temporary refs, while turns that changed files are stored in `SessionInfo.checkpoints` (capped at 200) for per-turn diff viewing. `/clear` and `delete()` remove all `refs/yi/checkpoints/<sid>/*`.
- Hidden side chats (`SessionInfo.sideChat`, `CreateParams.side_chat`, `SideChatTab.tsx`, `session_mcp.rs`):
  - Started via `/side [question]`, `/btw [question]`, the session "More" menu, the top-bar side chats menu, or the right panel's `+` menu. Creates a hidden child session (`parent_id = Some(main_id)`, `side_chat = true`) that stays out of the sidebar, overview, and global search (`isHostSession`), records no git checkpoints, and cascades deletion with its parent. Nesting a side chat inside another side chat is refused.
  - Lazy 3-layer context transfer (resolved on first launch/delivery in `spec_for` / `deliver`, without polluting stored `UserMessage` events):
    1. **Provider-native fork (when eligible)**: when the side chat uses the same `Claude` or `Codex` tool and account as its parent, the parent has an `external_id`, and the parent is currently idle with no background tasks, `StartSpec.fork_session = true` forks natively (`claude --resume <id> --fork-session`, Codex `thread/fork`) and prepends only a concise `<yi-side-context>` framing guardrail + `session_read` pointer (`side_chat_native_framing`). If native fork fails before ready (e.g. older CLI or missing rollout), Claude restarts in-place and Codex falls back to `thread/start`, transparently injecting the full portable digest (`fork_fallback_handoff`).
    2. **Budgeted portable context + live streaming capture**: for cross-provider side chats, ACP tools, busy parents, or fork fallbacks, `side_context_digest()` builds a 16,000-character budgeted `<yi-side-context>` block carrying the framing guardrail (do not continue/redo the main task or edit files unasked), the parent's current live streaming deltas (`SessionRt.live_text`) and active tool activity, and intact historical messages prioritized as latest user → latest assistant → first user goal → newest-to-oldest fill, listing omitted `seq` numbers for on-demand recovery.
    3. **Read-only related-session MCP (`yi_session`, `crates/yi-agentd/src/session_mcp.rs`)**: mounted on non-Bot structured AI sessions over local IPC (`session.mcp` + `proxy_access` PID binding, preauthorized across all 7 structured providers). Exposes strictly read-only `session_read` (status, live streaming text, `messages`/`activity` pagination, and exact `seq` + `textOffset` slicing within a 24,000-char response cap) and `session_list_related`, strictly scoped to the caller's parent/side-chat family.
  - Side chats inherit the parent tool, account, model, and effort by default (read-only `plan` permission where supported, else `default`), each reusing the main `Composer` (`<Composer compact />`) in `SideChatPane`. Conclusions are brought back to the main composer via "Add to chat" or `@`-mentioning the side chat (`ContextRef` `kind: 'side'`, including `sessionId` so the parent can read full details via `yi_session`), which works even while the main turn is running (queued on send). Closing an unused side chat tab deletes it automatically; used side chats remain reopenable from the parent session header's side chat menu until explicitly deleted.
