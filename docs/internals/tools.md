# Tool adapters

Per-tool details beyond [adding-a-tool.en.md](../adding-a-tool.en.md): detection, probing, permission modes, usage stats and each tool's quirks.

- Queries that don't belong to a session, such as model lists and quotas, live in `crates/yi-agentd/src/probe.rs`: start the tool once, ask, exit; the working directory is `<base>/probe`.
- Tool detection is `crates/yi-agentd/src/tools.rs`: `fix_path` builds the daemon's PATH (inherited PATH, `YI_CONSOLE_PATH`, the login shell's PATH on Unix, the registry's system + user PATH on Windows, then common install directories that exist), and `detect` looks up fixed executable names on it. The daemon outlives the app, so `tools.detect` reruns `fix_path` before scanning; the "Re-detect" entry in the new session page's tool menu and saving host settings both call it via `redetectTools` in `store.ts`.
- Tool versions and upgrades (`toolupdate.rs`; `HostTools.tsx`, a collapsible list at the bottom of each host card, collapsed by default, open state remembered per host, opened by any upgrade in progress): `tools.update` runs the tool's own updater (`claude update`, `codex update`, `cursor-agent update`, `kiro-cli update --non-interactive`, `qodercli update`, `codebuddy update`, `agy update`) with the detected executable, stdin closed, a 10-minute cap, and streams its output as `tools.updating` events; when it ends the daemon re-runs `fix_path` and detection and sends the new tool list. We never install a copy of our own (unlike OpenBot's managed runtimes), so each tool updates the way it was installed. One upgrade at a time per host. Sessions of that tool mid-turn (or queued / with background tasks) block it; on Windows, where a running .exe can't be replaced, idle chat sessions' processes are ended first (they restart on the next message) and live terminal sessions block it too (`Hub::tool_in_use`). `tools.latest` asks the npm registry (`npm_config_registry` if set) for the tools published there (Claude, Codex, CodeBuddy), cached 10 minutes, only when the list opens or on "Check for updates"; Cursor / Kiro / Qoder have no version to compare. It also returns the daemon's current detection, since the client's cached `hello` predates any upgrade.
- Status line values computed on the host (git status, custom command) are in `crates/yi-agentd/src/statusline.rs`. The command input reuses the JSON fields of Claude Code's statusLine; our own fields only go under `yi_console`.
- Which permission modes each tool supports is decided by `permission_modes(tool, mode)` in `hub.rs`, and `permModes` in the frontend's `app/src/perm.ts` is kept in sync by hand; the UI only lists modes the current tool supports. Modes reported back by the tool that we don't know (such as Claude's `dontAsk`) are recorded and shown by their raw name, never dropped.
- Usage stats (`stats.rs`): usage for Claude / Codex / Qoder / CodeBuddy is read from the tools' own logs (`~/.claude/projects`, `~/.codex/sessions`, `~/.qoder/projects`, `~/.codebuddy/projects`, cached by file mtime and size; Qoder's built-in models only record credits, CodeBuddy records both tokens and credits). For these four tools only cost (Claude) is taken from usage_log, to avoid double counting.
- Qoder (`qodercli --acp`) and CodeBuddy (`codebuddy --acp`) go through `acp.rs`; the arguments for entering ACP are in `acp_arg`. Both are Claude Code look-alikes: in terminal mode, like Claude, they pin the id with `--session-id` on first launch (`history::pins_session_id`), and session files are `<id>.jsonl` under `~/.qoder/projects` and `~/.codebuddy/projects` (`tool_session_exists` decides whether `--resume` works). Qoder's jsonl is Claude's format, so the history list and viewer reuse `scan_claude` / `read_claude`; CodeBuddy's is `{type:"message", role, content:[{input_text|output_text}]}`, only parsed for the list (`scan_codebuddy`), with content replayed by `session/load`. Qoder's ACP bridge forwards its subagents' streamed text, thinking and tool calls as the parent session's own updates with nothing to tell them apart, so while a foreground `Agent` / `Task` call runs, `acp.rs` drops chunks and new tool calls (as Claude's `parent_tool_use_id` messages are dropped); the subagent's report still arrives as that call's result. Qoder has no plan mode, and choosing "allow for this session" in its approvals switches it to acceptEdits, so auto-approval prefers `allow_once`. A failed CodeBuddy turn (e.g. not logged in) doesn't return a JSON-RPC error but `stopReason: refusal`, with the error in `_meta["codebuddy.ai/errorMessage"]` (`meta_error`); context usage comes from ACP's standard `usage_update` (with credits from `cost.amount`), while Qoder's context ratio comes from `context_usage_ratio` in the jsonl. Account quota (`probe.rs`): Qoder sends `get_usage_info` via `-p --no-session-persistence --input-format stream-json`; CodeBuddy gets a token from ACP's `_codebuddy.ai/getUserInfo` and then queries `get-user-resource-summary` with `User-Agent: codebuddy-code`. The gateway answers ureq's own agent with HTTP 403 / code 10085 and an empty quota body; that used to be swallowed and shown as "no quota data". The note is now the gateway's `msg` (401 with no message is still "log in again"). Empty sessions Qoder creates while probing models end up in its history, so they're deleted with `session/delete` afterwards.
- Codex subagents (multi_agent, on by default in Codex 0.166; checked against it): `codex app-server` streams every subagent thread's notifications on the same connection with that thread's `threadId`, and forwards their approval requests like the main thread's (answered the same way). `codex.rs` routes notifications whose `threadId` isn't the main thread to `sub_notification`, so a subagent's `turn/started` / `turn/completed` don't move `turn_id` or end the main turn, and its plan, deltas and reasoning stay out of the timeline. A spawn arrives in the parent as a `subAgentActivity` item (kind `started`, item id = the call id, `agentThreadId`, `agentPath`), shown as a `spawn_agent` ToolCall titled with the path's last segment (the prompt sent to the subagent is encrypted in the rollout, not available); `collabAgentToolCall` (`spawnAgent`, `wait`, `sendInput`…) is shown as `spawn_agent` / `wait_agent` / snake_case. The subagent's tool calls are emitted with `cx-sub:` ids (tagged "Subagent"), its last agentMessage of the first turn becomes the spawn call's ToolResult, and its token totals become Usage (tracked per thread, no context ratio). Running subagents are the session's background tasks (kind `local_agent`, id = thread id, see sessions.md), like Claude's: the main turn ends when Codex ends it, and the parent isn't woken when a subagent finishes (Codex doesn't do that), so a finish while the main thread is idle leaves a `后台任务完成：子 agent <name>` line. Stopping a task sends `turn/interrupt` for that thread's turn; Interrupt only stops the main turn. Neither stops a command already running: Codex lets it finish (the main thread's too). On history replay, `subAgentActivity` kind `completed` closes its spawn call with an empty result.
- Antigravity (`agy acp`, Google's successor to Gemini CLI) goes through `acp.rs`; checked against agy 1.5.7. Differences from the other ACP tools: the tool name is a top-level `name` on `tool_call` (`run_command`, `write_file`, `read_file`…; `ChatView.tsx` maps them, subagent tools `invoke_subagent` / `send_message` / `swarm` -> `Task`, and its PascalCase arguments `CommandLine` / `Path` / `Role` / `Prompt` / `Recipient` / `Message`…); `run_command` results are a "Created At / Completed At / Command exited with code N / Command output:" block that `antigravity_command_text` cuts down to the output plus an `exit code: N` line; subagent launches (`invoke_subagent`, `send_message` with `Recipient`, `swarm`) are asynchronous: the prompt returns `end_turn` right away with empty tool output, and when the subagent reports back agy wakes the parent by itself, outside any ACP prompt, so neither the subagent's work nor the parent's reply is streamed. `acp.rs` therefore defers those `ToolResult`s and follows the transcripts under `~/.gemini/antigravity-cli/brain/<id>/.system_generated/logs/transcript_full.jsonl` (`AgyWatch`, re-parsed only when size or mtime changes). The turn ends with the prompt, and running subagents (`local_agent`, `unstoppable: false`) and non-daemon background tasks (`run_command` as `local_bash`, `run_workflow` as `workflow`, one-shot `schedule` timers as `timer`; `IsDaemon` / recurring `CronExpression` tasks are left out so they don't block turn completion, and `in_progress` background calls stay tracked across the prompt-to-watch handoff) are the session's background tasks: background tasks expose their `Task logs are available at` `.log` path as `outputFile` and set `unstoppable: true` (hiding the Stop button in `BgTasks.tsx`, since ACP only exposes `session/cancel` for subagents), the subagent's tool calls are shown with `agy-sub:` ids (tagged "Subagent") while the session is idle, background tasks (a RUNNING GENERIC step with `Tool is running as a background task with task id: …`, output later in a `Task id "…" finished/canceled` or `sender=…` SYSTEM_MESSAGE; `schedule` timers with `TimerCondition` also settle silently when a matching message arrives) get their deferred `ToolResult`, a `后台任务完成/失败/已停止：<desc>` line marks each parent background task or subagent's end, and agy's wakeup of the parent streams live even while sibling background tasks continue running (reopening via Running, its steps emitted, and settling back to TurnEnd via `CycleEnd` if tasks remain, or ending with `session/resume` once all finish). The 20 s wakeup grace only times out if no wakeup response has started (`WAKEUP_GRACE`), never cutting off an active wakeup turn; if a new user prompt runs before `session/resume` or `session/load` re-emits muted tool calls, exact un-resumed wakeup prefixes and seen muted tool-call ids are deduplicated. The watch can't run during a prompt (the parent's own steps would look like a wakeup), so a new prompt moves running subagents and background tasks to `State.agy_carry` (settling any `SYSTEM_MESSAGE` that arrives mid-prompt via `poll_agy_prompt_bg`) and that prompt's watch adopts them. The watch gives up after 30 minutes without any transcript change. agy never sends a subagent's approval requests over ACP (the subagent sits in `waiting_for_input`), so allow-all launches `agy acp --dangerously-skip-permissions` (switching into or out of allow-all restarts the process, like Claude; the restart waits until no background task is left, see sessions.md), and in the other modes a subagent whose transcript ends in a tool call without a result for 30 s gets one error telling the user to stop it and switch. Stopping a task sends `session/cancel` for that subagent id (stops it; `session/close` doesn't); Interrupt only stops the parent's wakeup turn, subagents stay in the list; its ACP modes (`default`, `accept-edits`, `auto`, `plan`) cover every permission mode, so each one is set with `session/set_mode` (`State::native_modes`; allow-all stays in `default` and answers every request), and the tool's own mode changes map back; questions arrive as `session/request_permission` with an `interaction_` tool-call id and are never auto-answered. The session/prompt result carries ACP `usage` (inputTokens excludes cached reads: total = input + cachedRead + output), which becomes a `Usage` event; agy keeps no usage log we read, so stats count Yi Console sessions only, and there's no context ratio. Account quota (`probe.rs`) runs `agy -p /usage --output-format json` and `agy -p /credits …`: slash commands the CLI answers itself without a model turn, data under `command.data`; each model group (Gemini, Claude and GPT, Argon…) has a 5-hour and a weekly bucket with `remaining_fraction` and `reset_time`. Models: the values of its `model` config option (`gemini-4-argon`, `claude-opus-5-5`…) are the model list; `availableModels` lists every model+level pair (`claude-opus-5-5-high`), from which `antigravity_models` takes each model's `efforts`, and `currentModelId` is such a pair, so the current model is read from the option. The thinking level is the session's `effort`, set with `session/set_config_option` `thought_level` (`next_effort`); agy resets that option to its default on every model switch and announces it in `config_option_update`, so the level is set again whenever the tool reports a different value, and skipped when the model doesn't offer it (levels differ per model: Hydrogen has `xhigh`, GPT-OSS none). Terminal mode passes `--effort`. A used-up quota is not an error: the turn ends normally with the reply "⚠ Individual quota reached. … Resets in 4h9m8s.", which `antigravity_limit` turns into `limit_hit` (a reset within 5 hours is labelled the 5-hour window, otherwise weekly). MCP: stdio servers in `mcpServers` work (tool names are `mcp_<server>_<tool>`, `rawInput` adds a display-only `toolSummary` that agy doesn't forward, the results aren't reported in `tool_call_update`, and default mode doesn't ask before MCP calls); agy declares no `mcpCapabilities.http`, but an HTTP entry is accepted. Titles come from `session_info_update`. Not logged in shows up as `Authentication required` (-32000); we never call `authenticate` because its first method opens a browser on the host, the hint is `agy acp --login` (works over SSH). History is ACP `session/list` (`history::list_acp`; conversations are SQLite under `~/.gemini/antigravity-cli/conversations`, not readable, so no handoff file: chat mode hands off an exported Markdown like Cursor, and terminal mode has no hand-off entry); empty sessions created while probing models aren't listed. Terminal mode: `agy --conversation <id>`, `--model`, `--mode accept-edits|auto|plan`, `--dangerously-skip-permissions`; the id can't be pinned, so `guess_terminal_session` takes the newest session in the directory, like Cursor. Windows installs to `%LOCALAPPDATA%\agy\bin`.
- Codex reads its provider from `~/.codex/config.toml` (root `model_provider`, or the active `profile`'s): a provider other than `openai` replaces the login in `auth.json`, its key coming from the variable named by `env_key` (Windows: user/machine registry too). `accounts.rs` reads it with a small line parser (`codex_provider`; no TOML crate): the native status reports `actual` (provider, base URL, env key, whether it is set) instead of the ChatGPT identity, capture defaults to an API Key account for that provider (key from the env var, provider section kept; `source: "oauth"` captures the login and drops `model_provider` from the copied config), and every Codex account view carries `actual` from its own profile's config.toml. An OAuth account whose config selects a provider is shown as what it runs on, with `tools.accounts.convert` to turn it into an API Key account (login kept in `auth.json.oauth-bak`) or to drop the provider. API Key accounts on a custom provider get their key in the provider's `env_key` variable and no `OPENAI_BASE_URL` (it only applies to the built-in provider); editing the base URL rewrites the provider's `base_url`.
- Codex OAuth quota: `account/read` returning no account with `requiresOpenaiAuth` means the saved ChatGPT tokens can't be refreshed (e.g. a copied `auth.json` whose refresh token another copy already used). The probe fails with "登录已失效" and marks the account `needsLogin` until it is re-authenticated or recaptured, instead of reporting "no quota".
- Cursor's ACP doesn't report token usage or context: the context ratio is read from its `store.db` at turn end and on resume (`acp.rs`, see the comment there); per-turn token usage isn't available.
- Cursor ACP startup has a 60-second deadline until a session id is received. Authentication errors from `session/new` / `session/load` are surfaced with a login hint; the adapter never invokes `cursor_login` automatically, since it can open a browser and wait indefinitely on headless hosts. In-app account login remains the explicit path for browser authentication.
- Cursor in terminal mode gets no `--model` (`interactive_args` in `pty.rs`): chat-mode (ACP) model ids carry parameters like `grok-4.7[reasoning_effort=high,fast=true]`, the interactive UI often reports "Cannot use this model" on Windows, and mapping to the names from `--list-models` would need another cursor-agent run (about 8 s on Windows). Without it, Cursor uses the last choice recorded in `~/.cursor/cli-config.json`.
- Cursor chat model controls negotiate `clientCapabilities._meta.parameterizedModelPicker` in both ACP startup and model probes. `session/new` / `session/load` and `session/set_config_option` report model parameters; `SessionInfo.modelConfigOptions` persists their supported choices and current values per session. The model menu exposes Fast and Reasoning when reported (Fast can increase cost). Reasoning is identified by ACP category `thought_level`, with `reasoning` / `reasoning_effort` / `effort` aliases for saved sessions from older daemons; parameter ids are preserved when setting values. Controls with fewer than two choices are hidden; changes use `session.setModelConfig`, are serialized before the next prompt, and are restored after model selection when the adapter restarts. Unsupported saved values are skipped after a model/tool change; rejected changes restore the last reported state. Other ACP tools keep their existing model picker. Legacy Cursor model ids with bracketed parameters are restored through the parameterized picker.
- Cursor context usage reads the authoritative chat-mode store in `~/.cursor/acp-sessions/<id>/store.db` on resume and at turn end, falling back to `~/.cursor/chats/<workspace>/<id>/store.db` only when the ACP copy is absent. Looking only in `chats` hides usage for ACP-only sessions and can show stale values after switching interfaces.
- Cursor model-menu browser regression fixture: `app/tests/cursor-model-picker.html` and `cursor-model-picker.mjs` (run through windows-remote). It uses the real component with a mocked transport to check parameter RPCs, current-value badges, language changes, unsupported models, mobile sheets and back navigation. Adapter tests cover ordered requests, saved state and ACP-versus-terminal context store selection.

- Generic MCP settings (`DaemonSettings.mcp_servers`) are validated/redacted in `mcp.rs` and `server.rs`. Environment/header placeholders preserve secrets by server name and key; omitted settings preserve old servers for older clients. Claude/Codex receive process arguments; all four ACP providers receive standard session definitions. HTTP ACP configurations require advertised `mcpCapabilities.http`. Native CLI configuration is not rewritten. The built-in `yi_computer_use` name is reserved.
- `StartSpec.mcp_fingerprint` / `SessionRt.mcp_fingerprint` compare only enabled servers selected for the current provider. An idle chat adapter relaunches before sending the next message if its selection changed; settings changes mark a busy adapter's existing `restart_pending` path for relaunch after the current turn. Terminal adapters do not receive host MCP settings.
- Windows Computer Use adds its owned server to the same six-provider integration with a session/window grant enforced at the native gateway; see [computer-use.md](computer-use.md). General MCP documentation: [Chinese](../mcp.md), [English](../mcp.en.md).
- Cursor parameter definitions (without session-local values) are cached per model in the host daemon's SQLite `model_configs` table, shared across sessions and kept across restarts; an empty list is a known model without parameters. Only answers to `session/set_config_option` fill it: Cursor's `session/new` lists `mode` and `model` but not the model's parameters, so the adapter always switches explicitly after creating a session, even to the model Cursor is already on. `session.setModel` / `session.setModelConfig` take effect on the session at once (values reset to the model's defaults on a model change; parameters the new model lacks are not offered or sent) and are queued for the process; they never wait for Cursor. The user's values win over reported ones in later answers; an answer for another model only fills the cache. A model with no cache entry sets `modelConfigPending`: a running process reads it with its switch, otherwise `probe::cursor_model_config` switches an empty session in the session's directory, reads the parameters and switches back (Cursor remembers the last model). A failed model switch is retried once at once (Cursor reports a failed model-list request as "Invalid model value"), then again before the next user message; a refused parameter falls back to the value Cursor reports. Old model strings `model[k=v,…]` are read as model plus values, and the session keeps only the model once the values are in its parameters (at creation when cached, else with Cursor's first answer), so the footer and turn ends never show a stale `fast=true`. An empty answer never replaces cached parameters (Cursor's answers do get cut short: one cached "no parameters" for grok-4.7), and a cached empty list counts only after Cursor said so again since the daemon started (`stored_config`), so an old wrong entry is asked once more. The new session page shows the parameters too: `tools.modelConfig {model, cwd}` returns the cached list or runs the probe, the choices go to `session.create` as `modelConfig {id: value}` and are remembered in `new-session-prefs` as `config`; the overview quick start and "new session with the same settings" pass them as well. A remembered old model string loses its values there (they were what kept Fast on after it was turned off).
- Single-tool multi-account & API key management (`accounts.rs`, `account_login.rs`, `keyring.rs`; frontend `AccountManagerModal.tsx`, `HostTools.tsx`, `SettingsView.tsx`):
  - **Hybrid isolation (`AccountIsolation`)**: `Codex` (`CODEX_HOME`), `Claude` (`CLAUDE_CONFIG_DIR`; structured sessions started in `~` pass `--setting-sources user` so host `~/.claude/settings.json` isn't loaded as project settings over isolated account env), and all `ApiKey` profiles (`Isolated`) run concurrently across sessions with independent env/profile directories; OAuth tools using host-global auth (`Antigravity` OAuth, `Cursor`, `Kiro`, `Qoder`, `CodeBuddy`) use `HostActive` atomic file/OS-keyring snapshots (`keyring.rs`: macOS `security`, Windows CredMan, desktop Linux `secret-tool` when `DBUS_SESSION_BUS_ADDRESS` is set, no-op on headless Linux).
  - **Enrollment & conflict rule**: `tools.accounts.capture`, interactive/device-auth sign-in (`tools.accounts.loginStart`/`loginInput`/`loginCancel`), API Key / Base URL profiles (`tools.accounts.save` with redacted `"********"` preservation and `allowAutoFailover: false` default for API Key), and portable bundle `export`/`import`. Creating without an explicit `accountId` always creates a new profile (never overwrites existing profiles).
  - **All-account quota probing (`probe.rs`)**: `tools.quota` accepts optional `accountId`; `tools.quotas` probes `Isolated` / active accounts concurrently and probes inactive `HostActive` OAuth snapshots sequentially only when `refreshInactive: true` and no live host-bound session is running (`has_running_host_session`). Usage stats (`stats.rs`) remain aggregated across all account directories rather than split by account.
  - **Cursor `CURSOR_API_KEY` isolation, enrollment & quota**: In `cursor-agent`, `CURSOR_API_KEY` exchanges into an `api_key_token` JWT and by default reads/writes host `auth.json` (or macOS Keychain `cursor-api-key`), while ACP startup initially reuses any unexpired cached `accessToken` in `auth.json` and `login` checks wipe `auth.json` whenever `apiKey` is present. Cursor `ApiKey` profiles therefore run with `AGENT_CLI_CREDENTIAL_STORE=memory`, `CURSOR_API_KEY` (plus optional `CURSOR_API_ENDPOINT` from `baseUrl`) so credentials stay strictly in process memory without reading or polluting host OAuth state; Cursor `Oauth` profiles unset `CURSOR_API_KEY` / `CURSOR_AUTH_TOKEN` / `AGENT_CLI_CREDENTIAL_STORE` across structured sessions, terminal sessions (including `tmux`), `tools.models`, `tools.modelConfig`, `tools.quota`, `history.list`, and in-app `cursor-agent login` (`NO_OPEN_BROWSER=1`), sanitize stale `authInfo`/`privacyCache` in `cli-config.json` on snapshot swaps, and detect API-key pollution via both `apiKey` fields/keychain entries and `type == "api_key_token"` JWT claims (marking polluted OAuth profiles as `needsLogin` instead of silently falling back to an API key). Saving or importing a `CURSOR_API_KEY` validates it upfront via `POST /auth/exchange_user_api_key` + `DashboardService` (`GetCurrentPeriodUsage`, `GetPlanInfo`, `GetHardLimit`, `GetMe`) to populate email/plan and quota cache; `capture` supports explicit `source: "oauth" | "apiKey"` so local OAuth and host `CURSOR_API_KEY` (including Windows registry env vars) can each be imported independently; terminal-mode sessions support live account switching by terminating the old terminal/tmux process and relaunching with `--resume` under the new account's environment.
