# Tool adapters

Per-tool details beyond [adding-a-tool.en.md](../adding-a-tool.en.md): detection, probing, permission modes, usage stats and each tool's quirks.

- Queries that don't belong to a session, such as model lists and quotas, live in `crates/yi-agentd/src/probe.rs`: start the tool once, ask, exit; the working directory is `<base>/probe`.
- Tool detection is `crates/yi-agentd/src/tools.rs`: `fix_path` builds the daemon's PATH (inherited PATH, `YI_CONSOLE_PATH`, the login shell's PATH on Unix, the registry's system + user PATH on Windows, then common install directories that exist), and `detect` looks up fixed executable names on it. The daemon outlives the app, so `tools.detect` reruns `fix_path` before scanning; the "Re-detect" button in the new session dialog and saving host settings both call it via `redetectTools` in `store.ts`.
- Tool versions and upgrades (`toolupdate.rs`; `HostTools.tsx`, a collapsible list at the bottom of each host card, collapsed by default, open state remembered per host, opened by any upgrade in progress): `tools.update` runs the tool's own updater (`claude update`, `codex update`, `cursor-agent update`, `kiro-cli update --non-interactive`, `qodercli update`, `codebuddy update`) with the detected executable, stdin closed, a 10-minute cap, and streams its output as `tools.updating` events; when it ends the daemon re-runs `fix_path` and detection and sends the new tool list. We never install a copy of our own (unlike OpenBot's managed runtimes), so each tool updates the way it was installed. One upgrade at a time per host. Sessions of that tool mid-turn (or queued / with background tasks) block it; on Windows, where a running .exe can't be replaced, idle chat sessions' processes are ended first (they restart on the next message) and live terminal sessions block it too (`Hub::tool_in_use`). `tools.latest` asks the npm registry (`npm_config_registry` if set) for the tools published there (Claude, Codex, CodeBuddy), cached 10 minutes, only when the list opens or on "Check for updates"; Cursor / Kiro / Qoder have no version to compare. It also returns the daemon's current detection, since the client's cached `hello` predates any upgrade.
- Status line values computed on the host (git status, custom command) are in `crates/yi-agentd/src/statusline.rs`. The command input reuses the JSON fields of Claude Code's statusLine; our own fields only go under `yi_console`.
- Which permission modes each tool supports is decided by `permission_modes(tool, mode)` in `hub.rs`, and `permModes` in the frontend's `NewSession.tsx` is kept in sync by hand; the UI only lists modes the current tool supports. Modes reported back by the tool that we don't know (such as Claude's `dontAsk`) are recorded and shown by their raw name, never dropped.
- Usage stats (`stats.rs`): usage for Claude / Codex / Qoder / CodeBuddy is read from the tools' own logs (`~/.claude/projects`, `~/.codex/sessions`, `~/.qoder/projects`, `~/.codebuddy/projects`, cached by file mtime and size; Qoder's built-in models only record credits, CodeBuddy records both tokens and credits). For these four tools only cost (Claude) is taken from usage_log, to avoid double counting.
- Qoder (`qodercli --acp`) and CodeBuddy (`codebuddy --acp`) go through `acp.rs`; the arguments for entering ACP are in `acp_arg`. Both are Claude Code look-alikes: in terminal mode, like Claude, they pin the id with `--session-id` on first launch (`history::pins_session_id`), and session files are `<id>.jsonl` under `~/.qoder/projects` and `~/.codebuddy/projects` (`tool_session_exists` decides whether `--resume` works). Qoder's jsonl is Claude's format, so the history list and viewer reuse `scan_claude` / `read_claude`; CodeBuddy's is `{type:"message", role, content:[{input_text|output_text}]}`, only parsed for the list (`scan_codebuddy`), with content replayed by `session/load`. Qoder's ACP bridge forwards its subagents' streamed text, thinking and tool calls as the parent session's own updates with nothing to tell them apart, so while a foreground `Agent` / `Task` call runs, `acp.rs` drops chunks and new tool calls (as Claude's `parent_tool_use_id` messages are dropped); the subagent's report still arrives as that call's result. Qoder has no plan mode, and choosing "allow for this session" in its approvals switches it to acceptEdits, so auto-approval prefers `allow_once`. A failed CodeBuddy turn (e.g. not logged in) doesn't return a JSON-RPC error but `stopReason: refusal`, with the error in `_meta["codebuddy.ai/errorMessage"]` (`meta_error`); context usage comes from ACP's standard `usage_update` (with credits from `cost.amount`), while Qoder's context ratio comes from `context_usage_ratio` in the jsonl. Account quota (`probe.rs`): Qoder sends `get_usage_info` via `-p --no-session-persistence --input-format stream-json`; CodeBuddy gets a token from ACP's `_codebuddy.ai/getUserInfo` and then queries `get-user-resource-summary`. Empty sessions Qoder creates while probing models end up in its history, so they're deleted with `session/delete` afterwards.
- Cursor's ACP doesn't report token usage or context: the context ratio is read from its `store.db` at turn end and on resume (`acp.rs`, see the comment there); per-turn token usage isn't available.
- Cursor in terminal mode gets no `--model` (`interactive_args` in `pty.rs`): chat-mode (ACP) model ids carry parameters like `grok-4.7[reasoning_effort=high,fast=true]`, the interactive UI often reports "Cannot use this model" on Windows, and mapping to the names from `--list-models` would need another cursor-agent run (about 8 s on Windows). Without it, Cursor uses the last choice recorded in `~/.cursor/cli-config.json`.
- Cursor chat model controls negotiate `clientCapabilities._meta.parameterizedModelPicker` in both ACP startup and model probes. `session/new` / `session/load` and `session/set_config_option` report model parameters; `SessionInfo.modelConfigOptions` persists their supported choices and current values per session. The model menu exposes Fast and Reasoning when reported (Fast can increase cost). Reasoning is identified by ACP category `thought_level`, with `reasoning` / `reasoning_effort` / `effort` aliases for saved sessions from older daemons; parameter ids are preserved when setting values. Controls with fewer than two choices are hidden; changes use `session.setModelConfig`, are serialized before the next prompt, and are restored after model selection when the adapter restarts. Unsupported saved values are skipped after a model/tool change; rejected changes restore the last reported state. Other ACP tools keep their existing model picker. Legacy Cursor model ids with bracketed parameters are restored through the parameterized picker.
- Cursor context usage reads the authoritative chat-mode store in `~/.cursor/acp-sessions/<id>/store.db` on resume and at turn end, falling back to `~/.cursor/chats/<workspace>/<id>/store.db` only when the ACP copy is absent. Looking only in `chats` hides usage for ACP-only sessions and can show stale values after switching interfaces.
- Cursor model-menu browser regression fixture: `app/tests/cursor-model-picker.html` and `cursor-model-picker.mjs` (run through windows-remote). It uses the real component with a mocked transport to check parameter RPCs, current-value badges, language changes, unsupported models, mobile sheets and back navigation. Adapter tests cover ordered requests, saved state and ACP-versus-terminal context store selection.

- Generic MCP settings (`DaemonSettings.mcp_servers`) are validated/redacted in `mcp.rs` and `server.rs`. Environment/header placeholders preserve secrets by server name and key; omitted settings preserve old servers for older clients. Claude/Codex receive process arguments; all four ACP providers receive standard session definitions. HTTP ACP configurations require advertised `mcpCapabilities.http`. Native CLI configuration is not rewritten. The built-in `yi_computer_use` name is reserved.
- `StartSpec.mcp_fingerprint` / `SessionRt.mcp_fingerprint` compare only enabled servers selected for the current provider. An idle chat adapter relaunches before sending the next message if its selection changed; settings changes mark a busy adapter's existing `restart_pending` path for relaunch after the current turn. Terminal adapters do not receive host MCP settings.
- Windows Computer Use adds its owned server to the same six-provider integration with a session/window grant enforced at the native gateway; see [computer-use.md](computer-use.md). General MCP documentation: [Chinese](../mcp.md), [English](../mcp.en.md).
- Cursor parameter definitions (without session-local values) are cached per model in the host daemon's SQLite `model_configs` table, shared across sessions and kept across restarts; an empty list is a known model without parameters. Only answers to `session/set_config_option` fill it: Cursor's `session/new` lists `mode` and `model` but not the model's parameters, so the adapter always switches explicitly after creating a session, even to the model Cursor is already on. `session.setModel` / `session.setModelConfig` take effect on the session at once (values reset to the model's defaults on a model change; parameters the new model lacks are not offered or sent) and are queued for the process; they never wait for Cursor. The user's values win over reported ones in later answers; an answer for another model only fills the cache. A model with no cache entry sets `modelConfigPending`: a running process reads it with its switch, otherwise `probe::cursor_model_config` switches an empty session in the session's directory, reads the parameters and switches back (Cursor remembers the last model). A failed model switch is retried once at once (Cursor reports a failed model-list request as "Invalid model value"), then again before the next user message; a refused parameter falls back to the value Cursor reports. Old model strings `model[k=v,…]` are read as model plus values.
